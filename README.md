# InMyTicket

[![Backend CI](https://github.com/dongri-p/InMyTicket_JPA/actions/workflows/ci.yml/badge.svg)](https://github.com/dongri-p/InMyTicket_JPA/actions/workflows/ci.yml)

실제 공연 정보로 좌석을 고르고 예매·결제까지 해볼 수 있는 티켓 예매 사이트입니다.
여러 명이 같은 좌석을 동시에 눌러도 한 명만 예매되도록 만드는 데 가장 공을 들였고,
서버도 직접 구축해서 배포·운영하고 있습니다.

**데모: https://inmyticket.duckdns.org** · **API 문서(Swagger): https://inmyticket.duckdns.org/api/docs**

공연 목록·상세·좌석은 로그인 없이 볼 수 있고, 예매할 때 로그인합니다. 로그인 화면의 "체험 계정으로 둘러보기" 버튼을 누르면 가입 없이 바로 써볼 수 있습니다. 결제는 인증 없이 바로 끝나는 데모 결제와 토스페이먼츠 테스트 결제위젯 중에 고를 수 있고, 둘 다 실제로 청구되지 않습니다. 토스 결제에서 퀵계좌이체를 고르면 테스트 비밀번호 `000000`으로 끝까지 결제해 볼 수 있습니다.

## 무엇을 할 수 있나요

- KOPIS(공연예술통합전산망) Open API에서 실제 공연 정보(포스터, 공연 기간, 공연장)를 받아와 보여줍니다.
- 장르 메뉴(콘서트·뮤지컬/연극·클래식/국악·무용·기타), 제목 검색, 예매 상태(예매중·오픈예정·공연종료)·지역(서울·경기/인천·충청/강원·경상·전라/제주) 필터로 공연을 찾습니다. 예매할 수 있는 공연이 목록 앞쪽에 나옵니다.
- 회차를 고르고 좌석을 선택해 예매합니다. 같은 회차 좌석은 최대 4석까지 한 번에 예매할 수 있고, 결제도 한 번에 합니다. 결제하지 않고 10분이 지나면 좌석은 자동으로 풀립니다.
- 토스페이먼츠 테스트 결제위젯 또는 데모 결제로 결제하고, 마이페이지에서 취소하면 결제했던 PG로 환불까지 처리됩니다. 결제 금액과 주문번호는 서버가 예약과 맞는지 확인한 뒤 토스 승인 API를 호출합니다.
- 로그인은 JWT로 처리합니다.
- 관리자는 같은 사이트에서 공연장·회차를 등록하고 KOPIS 공연 정보를 다시 불러옵니다. 회차는 공연 기간 안의 앞으로의 시각으로만 등록되고, 같은 공연장에서 시작 시각이 3시간 안으로 겹치는 회차는 막습니다.

## 기술 스택

- **Backend**: Java 21, Spring Boot 3.5, Spring Data JPA, Spring Security + JWT, Flyway
- **DB**: MySQL 8.0 (운영), H2 (로컬·테스트)
- **Frontend**: React 19, Vite
- **Infra**: AWS EC2, Docker Compose, Nginx, Let's Encrypt, GitHub Actions, GHCR

## 구조

EC2 한 대에서 컨테이너 3개(nginx+프론트, 백엔드, MySQL)를 띄웠습니다. 외부에는 80/443만 열려 있고, 백엔드와 DB는 밖에서 직접 접근할 수 없습니다.

```mermaid

    User([브라우저]) -- HTTPS --> Nginx["frontend<br/>Nginx + React"]
    subgraph EC2["AWS EC2 · Docker Compose"]
        Nginx -- "/api/**" --> Backend["backend<br/>Spring Boot"]
        Backend --> DB[("MySQL 8.0")]

    Backend -- 공연 정보 동기화 --> KOPIS["KOPIS API"]
```

`main`에 push하면 GitHub Actions가 테스트 → 이미지 빌드(GHCR) → EC2 배포까지 이어서 진행합니다. 처음엔 EC2(RAM 1GB)에서 직접 빌드했는데, 빌드된 이미지를 받아오기만 하도록 바꾸면서 배포 단계가 2분 10초에서 25초 정도로 줄었습니다.

## 고민했던 문제들

각 항목의 자세한 과정은 [docs/problem-solving.md](docs/problem-solving.md)에 정리했습니다.

**1. 같은 좌석 동시 예매**
좌석을 조회할 때 비관적 락(`SELECT ... FOR UPDATE`)을 걸어 한 좌석은 한 요청만 차지할 수 있게 했고, 회차의 잔여석 수는 원자적 UPDATE로 줄입니다. 여러 좌석을 한 번에 예매할 때는 좌석을 id 순서로 한꺼번에 잠가서, 겹치는 좌석을 동시에 고른 두 요청이 서로를 기다리는 데드락이 생기지 않게 했습니다. 고른 좌석 중 하나라도 이미 예약됐으면 나머지도 예약되지 않습니다. 한 좌석에 예매 요청 100개를 동시에 보내는 테스트에서 성공은 정확히 1건이었고, 운영과 같은 MySQL 8.0에서 5번 반복해도 결과가 같았습니다.

**2. 결제 통신 동안 DB 커넥션을 붙잡고 있는 문제**
PG 승인 통신(약 1.5초)이 트랜잭션 안에 있으면 그동안 커넥션을 계속 쥐고 있게 됩니다. 통신은 트랜잭션 밖에서 하고, 결과를 저장하는 부분만 짧은 트랜잭션으로 분리했습니다. 운영과 같은 MySQL 8.0에서 측정해보니 결제 1건당 커넥션 점유 시간이 1,526.7ms에서 10.8ms로, 약 141배 줄었습니다. 그런데 실제 HTTP 요청에서는 OSIV 때문에 이 효과가 없었고, 6번에서 OSIV를 끈 뒤에야 적용됐습니다.

**3. PG 승인은 됐는데 DB 저장이 실패하면?**
2번처럼 나누고 나니 "돈은 빠져나갔는데 결제 기록이 없는" 경우가 생길 수 있었습니다. DB 반영이 실패하면 PG에 승인 취소를 보내는 보상 처리를 넣었습니다. 보상이 실패하면 수동 환불이 필요하다는 로그를 남기고, 이미 다른 결제에 쓰인 결제 키는 남의 결제를 환불하지 않도록 보상을 건너뜁니다.

**4. 결제 중인 예약의 상태 관리**
결제 중에 자동 만료 스케줄러가 좌석을 회수해버리지 않도록 `PROCESSING` 상태를 두었습니다. 그런데 PG 통신 도중 서버가 죽으면 이 상태에서 영원히 빠져나오지 못했습니다. 그래서 결제 시작 시각을 기록해두고, 5분이 지나도 `PROCESSING`이면 스케줄러가 `PENDING`으로 되돌리게 했습니다.

**5. 결제와 취소가 동시에 들어올 때**
락 없이 둘이 같은 예약을 수정하면 "결제는 완료인데 좌석은 반환된" 상태가 생겼습니다. 예약에도 비관적 락을 걸어 순서대로 처리되게 했습니다. 그리고 소유자 확인보다 환불 통신이 먼저 나가던 순서도 바로잡았습니다.

**6. 락을 걸고 다시 읽었는데 옛날 값이 나오는 문제**
외부 기술 피드백에서 지적받은 문제입니다. 자동 만료 스케줄러는 락 없이 후보 예약을 찾은 뒤, 락을 걸고 다시 읽어서 아직 `PENDING`인지 확인합니다. 그런데 JPA는 같은 영속성 컨텍스트에 이미 있는 엔티티를 DB에서 다시 읽어와도 덮어쓰지 않습니다. 그래서 그 사이 결제가 끝나도 `PENDING`으로 보여, 결제된 예약을 취소하고 좌석을 회수할 수 있었습니다. 후보는 id만 조회해서, 락을 거는 조회에서 엔티티가 처음 로딩되도록 바꿨습니다.
취소 API도 같은 문제가 있었습니다. OSIV가 켜져 있어서 트랜잭션을 나눠도 요청 하나 동안 영속성 컨텍스트를 같이 썼고, 취소 도중 결제가 끝나면 환불 없이 취소됐습니다. OSIV를 끄자 해결됐고, 2번의 커넥션 점유 개선도 이때 비로소 실제 요청에 적용됐습니다(결제 API 기준 약 1,517ms → 15ms 이하). 두 경우 모두 수정 전 코드에서 실패하는 테스트를 먼저 만들어 확인했습니다.

**7. 로그인 보안**
아이디가 없을 때와 비밀번호가 틀렸을 때 메시지와 응답 시간이 달라서 계정이 있는지 알아낼 수 있었습니다. 둘을 똑같이 맞췄습니다. 5회 실패 잠금은 (아이디, IP) 기준인데, nginx 뒤라서 모든 요청의 IP가 nginx로 찍히고 있었습니다. 이걸 그대로 두면 누구든 남의 계정을 잠글 수 있어서, 신뢰하는 프록시의 `X-Forwarded-For`만 읽도록 설정했습니다.

**8. N+1 쿼리**
회차 목록을 조회할 때 공연·공연장을 회차마다 따로 조회하고 있었습니다. 페치 조인으로 쿼리 1번에 가져오도록 바꿨습니다.

**9. 공연 기간 밖의 회차**
KOPIS에서 공연 기간을 받아오면서도 저장하지 않아서, 11월 7일~14일 공연에 11월 21일 회차를 등록해도 막히지 않았습니다. 기간을 저장하고(Flyway V7) 회차 등록 때 기간 밖 날짜는 거절하도록 했습니다. 이미 운영 DB에 있던 공연 100건은 기간이 비어 있어서, 서버가 뜰 때 KOPIS 상세 조회로 빈 값만 채우게 했습니다.
그런데 운영과 같은 MySQL 환경에서 돌려보니 90건 중 앞 8건만 채워졌습니다. KOPIS가 간격 없이 연달아 들어오는 요청에 400을 돌려주고 있었고, 호출 사이에 200ms 간격을 두자 90건 중 88건이 채워졌습니다. 실패한 공연은 다음 기동 때 다시 시도합니다.

**10. 테스터 피드백 반영**
지인들에게 써 보게 했더니, 지난 회차도 좌석 선택까지 들어간 뒤에야 예매가 막히고, 아이디에 공백이 들어가고, 예매할 수 있는 공연이 목록 뒤쪽에 묻혀 있다는 의견이 나왔습니다. 목록은 "예매중 → 오픈예정 → 공연종료" 순으로 정렬하고 같은 기준으로 상태 필터를 만들었습니다. 처음엔 정렬 기준이 회차 테이블에 있어서 JPQL `case` 식으로 작성했는데, 데이터를 늘려 보니 이 식이 가장 큰 병목이어서 지금은 컬럼으로 저장합니다(13번).

**11. KOPIS 키가 잘못돼도 "성공"**
KOPIS는 키가 잘못돼도 HTTP 200에 정상 응답과 같은 XML 구조로 에러 코드만 담아 보냅니다. 응답 객체에 그 필드가 없어서 모든 값이 비어 있는 "빈 공연"으로 읽혔고, 동기화는 성공으로 끝났습니다. 에러 코드가 있으면 공연이 아니라 에러로 보고 로그를 남기도록 했고, 저장 직전에도 apiId나 제목이 빈 항목은 건너뜁니다. 실제 에러 XML을 돌려주는 로컬 HTTP 서버로 테스트했습니다.

**12. API 응답 규칙이 제각각이던 문제**
이것도 외부 기술 피드백에서 지적받았습니다. 공연의 예매 상태는 응답(KOPIS 한글 값)과 필터(`ON_SALE` 등)가 기준이 달랐고, 목록 배지는 프론트가 따로 계산하고 있었습니다. 서버가 계산한 `bookingStatus` 하나로 응답·필터·배지를 맞췄습니다. 생성 API는 201과 `Location` 헤더, 취소는 `POST /reservations/{id}/cancel`과 204로 바꿨습니다(예약을 지우지 않고 상태만 바꾸고 환불하는 동작이라 `DELETE`가 맞지 않았습니다). URL이 가리키는 공연·회차·예약이 없으면 400 대신 404를 주고, 없는 경로나 다른 메서드는 500이 아니라 404/405로 응답합니다. 공연 목록 "더 보기"는 OFFSET 대신 커서(직전 페이지 마지막 공연의 정렬 키)로 이어 받게 해서, 첫 페이지를 본 사이 공연이 추가돼도 다음 페이지에 같은 공연이 다시 나오지 않습니다.
에러 응답에는 `code`를 넣었습니다. 같은 409라도 "이미 예매된 좌석"(`SEAT_ALREADY_RESERVED`)과 "결제 진행 중"은 화면이 다르게 대응해야 해서, 좌석을 고르는 사이 다른 사람이 먼저 예매하면 화면이 이 코드를 보고 좌석 현황을 새로 불러옵니다. 결제는 같은 요청이 다시 와도 안전하게 했습니다. 이전에는 PG 승인은 됐는데 응답을 못 받은 클라이언트가 재시도하면 409가 나가 "돈은 빠졌는데 실패"로 보였습니다. 이제 토스의 `paymentKey`를 멱등성 키로 써서 같은 결제면 PG를 다시 부르지 않고 처음 결과를 돌려주고, 이미 쓰인 키로 다른 예약을 결제하려 하면 PG 승인 전에 막습니다.

**13. 데이터를 늘리자 공연 목록이 다른 API까지 느리게 만든 문제**
외부 기술 피드백에서 "데이터를 늘려서 측정해 보라"는 의견을 받고, 로컬 MySQL에 회원 10만·공연 10만·좌석 350만·예매 117만 건을 넣은 뒤 k6로 100명이 목록 → 상세 → 회차 → 좌석 → 내 예매를 반복하게 했습니다. 전체 p95가 1.84초였습니다. 실행계획을 보니 공연 목록이 20건을 보여주려고 공연 10만 건을 다 읽고 행마다 회차 서브쿼리를 돌린 뒤 정렬하고 있었고(한 번에 150ms), 이 쿼리가 커넥션을 오래 잡는 바람에 혼자 부르면 10ms인 좌석 조회까지 p95 740ms로 밀렸습니다. 예매 상태를 컬럼으로 저장하고 `(예매 상태, id)` 인덱스 순서대로 읽게 바꿨고(0.12ms), 그다음 병목이던 첫 페이지 전체 건수는 인덱스에 장르를 붙이고 필터 조합별로 30초 캐시했습니다.

| 100명 동시, 60초 | 전체 p95 | 공연 목록 p95 | 처리량(회/초) |
| --- | --- | --- | --- |
| 처음 | 1.84s | 2.73s | 27 |
| 예매 상태를 컬럼 + 인덱스로 | 440ms | 575ms | 100 |
| 건수 인덱스 + 30초 캐시 | 214ms | 257ms | 167 |

300명에서는 p95 442ms였습니다. 측정 스크립트와 결과는 [perf/](perf/)에 있습니다.

**14. 결제가 몰리자 좌석 조회까지 느려진 문제**
13번은 조회만 쟀어서, 예매와 결제(데모 PG 1.5초)를 섞어 다시 쟀습니다. 1,000명이 좌석 20개를 동시에 예매하면 매번 정확히 20건만 성공했고, 끝나고 DB를 확인해도 중복 티켓이나 잔여석 불일치는 0건이었습니다. 그런데 300명이 각자 예매·결제를 하자 혼자 부르면 10ms인 좌석 조회까지 p95 590ms로 느려졌습니다. 부하 중에 스레드 덤프를 떠 보니 Tomcat 요청 스레드 200개 중 199개가 PG 응답을 기다리고 있었고, DB 커넥션을 기다리는 스레드는 0개였습니다. PG를 기다리는 동안 DB 커넥션은 안 잡게 해 두었지만(2·6번) 요청 스레드는 붙잡고 있었던 것입니다. Java 21로 올리고 요청을 가상 스레드에서 처리하게 바꿨습니다(코드는 그대로).

| 300명 예매·결제, 60초 | 결제 성공 | 예매 p95 | 좌석 조회 p95 |
| --- | --- | --- | --- |
| 플랫폼 스레드 (Tomcat 200) | 7,597건 | 680ms | 590ms |
| 가상 스레드 | 10,905건 | 231ms | 193ms |

**15. 쿼리보다 트랜잭션 부가 명령이 더 많던 문제**
13번 부하에서 DB가 받은 명령을 세 보니, `@Transactional` 하나마다 실제 쿼리 외에 `SET autocommit` 2번, `SET SESSION TRANSACTION READ ONLY/READ WRITE`, `COMMIT`이 붙어 부가 명령이 실제 쿼리의 4배가 넘었습니다. 커넥션을 처음부터 autocommit=false로 두고(Hikari + Hibernate `provider_disables_autocommit`), read-only 표시는 서버에 보내지 않게 해서(Connector/J `readOnlyPropagatesToServer=false`) 트랜잭션당 명령을 6개에서 2개(쿼리 + COMMIT)로 줄였습니다. 같은 100명 부하에서 60초 반복 횟수가 약 1.5만 → 2.7~3.2만, 전체 p95가 138~161ms → 62~77ms가 됐습니다. 대신 읽기 전용 메서드에서 실수로 쓰는 걸 DB 서버가 막아 주지는 않습니다. 커넥션 풀은 20·40으로 늘려도 결제 처리량이 그대로여서 10으로 두었습니다.

## 배포하면서 겪은 문제

EC2(t2.micro)에 올리면서 겪은 일들입니다. 자세한 내용은 [docs/deployment-troubleshooting.md](docs/deployment-troubleshooting.md)에 있습니다.

- HTTP로 배포했더니 결제 화면이 흰 화면이 됨 → `crypto.randomUUID()`가 HTTPS에서만 동작해서였고, 도메인과 인증서를 붙여 HTTPS로 전환
- 메모리·디스크 부족으로 빌드 실패 → 스왑 추가, EBS 확장, 이후 빌드를 GitHub Actions로 이전
- 재시작하면 IP가 바뀌어 접속 불가 → Elastic IP 할당
- 백엔드만 재배포하면 502 → nginx가 백엔드 주소를 처음 한 번만 조회해서였고, 도커 DNS로 요청마다 다시 조회하게 변경
- `.env`를 바꿔도 관리자 비밀번호가 안 바뀜 → 기동 시 비교해서 갱신
- 토스 테스트 결제가 갑자기 "알 수 없는 에러"로 안 열림 → 쓰던 토스 문서 공개 테스트 키(API 개별 연동 키)를 토스가 막아서였음. 결제창 방식은 이 키만 받는데 전자결제 신청 전에는 발급되지 않아서, 테스트 키로 쓸 수 있는 결제위젯 방식으로 전환
- 백엔드 8080 포트가 외부에 열려 있었음 → 포트 매핑과 보안 그룹 규칙 제거
- 회차 시간이 DB에 9시간 밀려 저장됨 → JVM 타임존을 Asia/Seoul로 맞추고 밀린 데이터 보정

## 아직 부족한 점

- 동시성 테스트를 MySQL 8.0으로 돌린 건 로컬 Docker에 직접 연결해서였고, CI에서는 아직 H2로만 돕니다. MySQL과 H2는 락 동작이 달라서 Testcontainers로 CI에서도 MySQL 기준으로 돌리려고 합니다.
- 부하 테스트(13·14번)는 k6·앱·MySQL을 한 PC에서 돌린 로컬 측정이라, 운영 서버(t2.micro)에서의 수치와는 다릅니다. 커넥션 풀 크기(10)도 로컬 측정을 근거로 정한 것이라, 운영에서 다시 확인이 필요합니다.
- 토스 결제는 테스트 키(토스 문서 공개 결제위젯 키)로만 연동했습니다. 공개 키라 이전 키처럼 토스가 막으면 결제가 안 열리고, 그때는 제 상점 키로 바꿔야 합니다. 방문자가 결제 단계 없이 바로 체험할 수 있게 데모 결제도 함께 두었습니다. 데모 결제는 이름 그대로 결제 없이 승인되는 경로입니다.
- 서버 재시작 후 `PROCESSING` 예약을 복구할 때 PG 거래 조회로 승인 여부를 확인하지 않고, 결제 기록이 없으면 미승인으로 봅니다. 토스 승인 요청이 타임아웃 나도 같은 이유로 미승인으로 처리합니다.
- 좌석은 비관적 락으로 지키고 있어서 `@Version`(낙관적 락)이 실제로 막아주는 경로는 지금 없습니다. 락 없이 좌석을 바꾸는 코드가 생길 때를 대비한 안전장치 정도입니다.
- 로그인 잠금은 서버 메모리에 저장해서 재시작하면 초기화되고, 여러 IP로 나눠서 하는 공격은 막지 못합니다.
- 관리자 화면을 따로 두지 않고 같은 로그인에서 권한(role)으로만 나눴습니다. 화면에서 관리자 메뉴를 숨기는 건 표시용이고, 실제 권한 검사는 서버가 합니다.
- 회차 중복은 러닝타임을 저장하지 않아서 "같은 공연장에서 시작 시각이 앞뒤 3시간 안"이라는 고정 기준으로만 봅니다. 3시간이 넘는 공연이면 실제로는 겹쳐도 통과합니다. 또 검사와 저장 사이에 락이 없어서, 관리자 두 명이 동시에 같은 시간대를 등록하면 둘 다 들어갈 수 있습니다. KOPIS에 공연 기간이 없는 공연은 기간 검사를 건너뜁니다.
- 공연 목록에 날짜순 정렬은 없습니다. 지역 필터는 KOPIS 시·도 이름을 권역으로 묶은 목록으로 거르기 때문에, 행정구역 이름이 바뀌어 목록에 없는 지역이 생기면 그 공연은 '전체'에서만 보입니다. (실제로 광주·전남이 '전남광주통합특별시'로 내려와서 새 이름과 옛 이름을 함께 넣어 두었습니다.)
- 지역 필터 값(`GYEONGGI_INCHEON` 등)은 화면의 칩 구성을 그대로 API 값으로 쓴 것이라, 칩을 "경기"와 "인천"으로 나누기만 해도 API가 바뀝니다. 서버는 시·도 단위 코드로 받고, 권역으로 묶는 건 화면이나 별도 매핑 테이블에서 하는 게 맞다고 봅니다. 지금은 이 구조로 두었습니다.
- 공연 목록의 예매 상태는 저장해 둔 값이라, 마지막 회차가 시작되거나 종료일이 지나서 바뀌는 건 1분마다 도는 스케줄러가 반영합니다. 그 사이 최대 1분은 목록에 예매중으로 보일 수 있습니다(예매는 회차 시각을 따로 검사해서 지난 회차가 팔리지는 않습니다). 그룹이 바뀌는 순간 페이지 경계에 걸린 공연은 한 번 중복되거나 빠질 수 있습니다. 목록 전체 건수도 최대 30초 늦게 반영됩니다.
- 멱등성은 결제에만 적용했습니다. 예매 요청을 두 번 보내면 두 번째는 자기가 방금 잡은 좌석 때문에 `SEAT_ALREADY_RESERVED`를 받습니다. 화면에서는 버튼을 막아 두었지만, API 수준에서는 `Idempotency-Key` 헤더 같은 장치가 필요합니다.
- 공연장은 이름만 저장해서, 상세 화면의 위치는 공연장 이름으로 네이버 지도를 검색하는 링크로 대신합니다. KOPIS 공연시설 API로 주소·좌표를 받으면 지도를 직접 띄울 수 있습니다.
- 배포할 때 백엔드가 뜨는 20초 정도는 API가 502를 반환합니다. DB 백업은 도커 볼륨뿐이고, 모니터링은 `docker logs`로 보는 수준입니다.

<summary>API 목록</summary>

요청·응답 형식과 에러 코드 전체 표는 [Swagger 문서](https://inmyticket.duckdns.org/api/docs)에서 보고 바로 호출해 볼 수 있습니다. 회원 API는 로그인 응답의 `accessToken`을 Authorize에 넣으면 됩니다.

| Method | URL | 설명 | 권한 |
| --- | --- | --- | --- |
| POST | `/api/v1/members` | 회원가입 | 전체 |
| POST | `/api/v1/members/login` | 로그인 (JWT 발급) | 전체 |
| GET | `/api/v1/members/{memberId}` | 회원 정보 (본인만) | 회원 |
| GET | `/api/v1/performances` | 공연 목록 (커서 페이지네이션 `cursor`·`size`, `genre` 장르·`keyword` 제목 검색·`status` 예매 상태·`region` 지역, 예매중 공연 먼저) | 전체 |
| GET | `/api/v1/performances/{id}` | 공연 상세 | 전체 |
| GET | `/api/v1/performances/{performanceId}/schedules` | 공연별 회차 목록 | 전체 |
| GET | `/api/v1/schedules/{scheduleId}` | 회차 단건 | 전체 |
| GET | `/api/v1/schedules/{scheduleId}/seats` | 회차별 좌석 현황 | 전체 |
| POST | `/api/v1/reservations` | 좌석 예매 | 회원 |
| GET | `/api/v1/reservations/me` | 내 예매 목록 | 회원 |
| GET | `/api/v1/reservations/{reservationId}` | 예매 단건 (본인만) | 회원 |
| POST | `/api/v1/reservations/{reservationId}/cancel` | 예매 취소 (결제 건은 환불) | 회원 |
| POST | `/api/v1/payments` | 결제 승인 (`provider`: TOSS·DEMO, 결제창의 `paymentKey`·`orderId`·`amount`) | 회원 |
| GET | `/api/v1/payments/{paymentId}` | 결제 단건 (본인 예약의 결제만) | 회원 |
| POST | `/api/v1/performances/sync` | KOPIS 공연 정보 동기화 | 관리자 |
| GET | `/api/v1/halls` | 공연장 목록 | 관리자 |
| GET | `/api/v1/halls/{hallId}` | 공연장 단건 | 관리자 |
| POST | `/api/v1/halls` | 공연장 등록 | 관리자 |
| POST | `/api/v1/schedules` | 회차 등록 (공연 기간 안의 날짜만) | 관리자 |

생성은 201 + `Location` + `{id}`(`Location`은 위 단건 조회 주소), 취소·동기화는 204(본문 없음), 목록은 `{count, totalCount, data}`(공연 목록은 다음 페이지가 있으면 `nextCursor`), 에러는 `{status, code, message}`입니다(`code` 예: `SEAT_ALREADY_RESERVED`, `PAYMENT_ALREADY_PROCESSING`, `LOGIN_LOCKED`). 같은 `paymentKey`로 결제를 다시 요청하면 처음과 같은 201과 결제 id를 돌려줍니다.
