# 배포하면서 겪은 문제 (자세히)

[README로 돌아가기](../README.md)

로컬에서는 잘 되다가 EC2(t2.micro)에 올리고, HTTP에서 HTTPS로 바꾸는 과정에서 드러난 문제들입니다.

## 1. HTTP로 배포했더니 결제 화면이 흰 화면

로컬에서는 멀쩡하던 결제 화면이 IP 주소(HTTP)로 접속하니 흰 화면만 나왔습니다. 콘솔을 보니 결제 키를 만들 때 쓴 `crypto.randomUUID()`가 `undefined`였습니다. 이 API는 HTTPS나 localhost 같은 보안 컨텍스트에서만 제공됩니다. `useEffect` 안에서 TypeError가 나면서 React 화면 전체가 내려간 것이었습니다.

일단 `crypto.getRandomValues()`로 대신 만드는 함수로 바꿔서 화면부터 살렸습니다. 그다음 DuckDNS 도메인과 Let's Encrypt 인증서를 붙여 서비스 전체를 HTTPS로 옮겼습니다.

## 2. 메모리·디스크 부족

RAM 1GB 인스턴스 한 대에서 백엔드·프론트·MySQL을 빌드하고 실행하려니 빌드가 중간에 죽거나 백엔드가 뜨지 못했습니다. 이미지를 계속 다시 빌드하다 보니 `ENOSPC`(디스크 부족)도 났습니다.

- 스왑 메모리를 추가하고, EBS 볼륨을 20GiB로 늘렸습니다(`growpart`, `resize2fs`).
- 바뀐 서비스만 다시 빌드하도록 했습니다(`up -d --no-deps <서비스>`). `depends_on` 때문에 그냥 `up --build frontend`를 하면 백엔드까지 같이 빌드됐습니다.
- 나중에는 빌드를 아예 GitHub Actions로 옮겼습니다. EC2는 GHCR에서 이미지를 받아오기만 해서 배포 단계가 2분 10초에서 25초 정도로 줄었고, 매 배포마다 안 쓰는 이미지를 정리합니다.

## 3. 재시작했더니 SSH 접속 불가

인스턴스를 재시작한 뒤 SSH가 안 붙어서 보안 그룹부터 봤습니다. 그런데 원인은 퍼블릭 IP가 재시작할 때마다 바뀌는 것이었습니다. IP가 바뀌면 CORS 허용 주소, 프론트에 들어간 API 주소도 같이 틀어집니다. Elastic IP를 할당해 고정하고 도메인을 그 IP에 연결했습니다.

## 4. 백엔드만 재배포하면 502

백엔드 컨테이너만 다시 띄우면 사이트는 열리는데 API가 전부 502였습니다. nginx는 `proxy_pass http://backend:8080`의 `backend`를 기동할 때 한 번만 IP로 바꿔서 기억합니다. 그래서 백엔드 컨테이너가 새 IP를 받아도 예전 IP로 계속 요청을 보내고 있었습니다.

처음엔 배포 스크립트에서 백엔드를 띄운 뒤 nginx 컨테이너도 재시작하는 걸로 넘어갔습니다. 하지만 원인이 DNS 캐시라서, 도커 내장 DNS를 resolver로 지정하고 `proxy_pass`에 변수를 넣었습니다. 이렇게 하면 요청할 때마다 다시 조회합니다.

```nginx
resolver 127.0.0.11 valid=10s;

location /api/ {
    set $backend_upstream http://backend:8080;
    proxy_pass $backend_upstream;
}
```

로컬 도커에서 백엔드 컨테이너를 지웠다가 다시 만들어 IP를 바꿔봤습니다. 기존 설정은 502가 났고, 바꾼 설정은 새 IP로 바로 200을 받았습니다. 지금 배포 스크립트는 재시작 대신 `nginx -s reload`만 합니다.

남은 문제는 백엔드가 기동하는 20초 정도 동안은 여전히 502가 난다는 점입니다. healthcheck를 두고 기동이 끝난 뒤 트래픽을 넘기는 방식으로 줄일 수 있을 것 같습니다.

## 5. `.env`를 바꿔도 관리자 비밀번호가 그대로

관리자 계정은 처음 기동할 때 `ADMIN_PASSWORD` 환경변수로 만들어집니다. 그런데 계정이 이미 있으면 생성을 건너뛰어서, `.env`를 바꿔도 DB의 비밀번호 해시는 그대로였습니다. 기동할 때 저장된 해시와 환경변수를 비교해서 다르면 갱신하도록 바꿨습니다. 이제 `.env`를 고치고 백엔드만 다시 띄우면 비밀번호가 바뀝니다.

## 6. 백엔드 포트가 밖에 열려 있었음

HTTPS와 리버스 프록시를 붙인 뒤에도 8080 포트가 열려 있어서 nginx를 거치지 않고 API를 직접 부를 수 있었습니다. compose에서 백엔드 포트 매핑을 지우고 보안 그룹의 8080 규칙도 삭제했습니다. 지금 열린 포트는 22, 80, 443뿐입니다.

## 7. 시간이 9시간 밀려 저장됨

백엔드 컨테이너의 JVM이 UTC로 돌고 있었고, JDBC 설정은 `serverTimezone=Asia/Seoul`이었습니다. 이 조합 때문에 관리자가 입력한 회차 시간이 DB에는 9시간 밀려 저장되고 있었습니다. 읽을 때 다시 역변환돼서 화면에서는 티가 안 났습니다. JVM 타임존을 `Asia/Seoul`로 맞추자 그동안 밀려 있던 값이 드러났습니다. 회차 시작 시간만 9시간 되돌렸습니다.

한 번은 예약·결제 시각까지 같이 되돌렸다가 다시 원복했습니다. 그 값들은 서버의 `now()`로 만든 거라 원래 맞는 값이었습니다. 시각 데이터는 어디서 만들어졌는지에 따라 따로 판단해야 한다는 걸 배웠습니다.
