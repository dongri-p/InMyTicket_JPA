# 고민했던 문제들 (자세히)

[README로 돌아가기](../README.md)

## 1. 같은 좌석 동시 예매

인기 공연은 남은 좌석 하나에 여러 명이 동시에 예매를 누릅니다. 처음 구현에서는 "좌석이 비었는지 확인 → 예약 처리"가 두 단계로 나뉘어 있었습니다. 그래서 두 요청이 동시에 "비어 있음"을 보고 둘 다 예약에 성공할 수 있었습니다.

- 좌석을 조회할 때 비관적 락(`@Lock(PESSIMISTIC_WRITE)`)을 걸어, 먼저 락을 잡은 요청이 끝날 때까지 다른 요청은 기다리게 했습니다. 기다렸다가 들어온 요청은 이미 예약된 좌석이라 실패합니다.
- 회차의 잔여석 수는 좌석과 성격이 달라서 락을 잡지 않고 `UPDATE ... SET available = available - 1` 같은 원자적 UPDATE로 처리했습니다.
- 취소처럼 좌석 여러 개를 한 번에 잠글 때는 항상 id 순서로 잠가서, 두 트랜잭션이 서로의 락을 기다리는 데드락을 피했습니다.

`ExecutorService`와 `CountDownLatch`로 한 좌석에 예매 요청 100개를 동시에 보내는 테스트(`ReservationServiceTest`)를 만들었고, 성공은 항상 1건입니다.

다만 이 테스트는 H2(TCP 모드)에서 돌렸습니다. MySQL과 H2는 락 동작이 다를 수 있어서, Testcontainers로 MySQL 기준 테스트를 추가하는 게 다음 과제입니다.

좌석 엔티티에는 `@Version`도 붙어 있습니다. 비관적 락을 거치지 않는 수정 경로가 생기면 그걸 잡아내려는 목적이었습니다. 그런데 지금 코드에서 좌석 상태를 바꾸는 곳은 모두 비관적 락을 거칩니다. 그래서 현재는 실제로 동작할 일이 없는 안전장치에 가깝습니다.

## 2. 결제 통신 동안 DB 커넥션을 붙잡고 있는 문제

결제는 "PG에 승인 요청 → 결과를 DB에 저장" 순서입니다. 처음엔 이걸 `@Transactional` 메서드 하나에 넣었습니다. 그러면 PG 응답을 기다리는 1.5초 동안 DB 커넥션을 계속 쥐고 있게 됩니다. 커넥션 풀은 기본 10개라서, 결제가 몰리면 결제와 상관없는 조회 API까지 커넥션을 못 받고 대기하게 됩니다.

- `PaymentService`: 트랜잭션 없이 PG 통신만 담당합니다.
- `PaymentApprovalService`: PG 승인이 끝난 뒤 결제 저장과 예약 확정만 짧은 트랜잭션으로 처리합니다.

`ConnectionHoldTimeMeasurementTest`에서 실제 HikariPool로 결제 1건당 커넥션 점유 시간을 쟀습니다.

| | 커넥션 점유 시간 |
| --- | --- |
| 트랜잭션 안에서 PG 통신 (개선 전) | 평균 약 1,517ms |
| 트랜잭션 분리 (현재) | 3~4ms |

단건 측정이라 "동시에 몇 건까지 버티는지"는 아직 보여주지 못합니다. k6로 동시 결제 상황에서 대기 시간과 실패율을 비교해보려고 합니다.

## 3. PG 승인은 됐는데 DB 저장이 실패하면?

2번처럼 트랜잭션을 나누면, PG 승인과 DB 저장을 하나로 묶어 롤백할 수 없습니다. 승인 후 DB 저장이 실패하면 고객 돈은 빠져나갔는데 결제 기록은 없는 상태가 됩니다.

그래서 `processPayment()`를 두 단계로 나눴습니다.

1. PG 승인이 실패하면: 빠져나간 돈이 없으니 예약만 `PENDING`으로 되돌립니다.
2. PG 승인 후 DB 저장이 실패하면: PG에 승인 취소를 먼저 보내고(보상), 그다음 `PENDING`으로 되돌립니다.

보상을 넣으면서 두 가지를 더 챙겼습니다.

- 보상 요청마저 실패할 수 있습니다. 이때 원래 실패 원인이 가려지지 않게 그대로 던지고, "수동 환불이 필요하다"는 에러 로그와 결제 키를 남깁니다.
- 이미 다른 결제에 쓰인 결제 키로 요청이 들어오면 unique 제약 때문에 DB 저장이 실패합니다. 이때 그 키로 승인 취소를 보내면 다른 사람의 정상 결제가 환불됩니다. 그래서 DB에 이미 기록된 키면 보상을 건너뜁니다. 실제 PG라면 이미 처리된 키는 PG 쪽에서 거절할 테지만, 시뮬레이션 PG는 그렇지 않아서 서버에서 막았습니다.

이 경우들은 실제 DB로 재현하기 어려워서 PG 클라이언트(`PgClient`)를 목으로 바꾼 단위 테스트(`PaymentServiceCompensationTest`)로 확인했습니다.

## 4. 결제 중인 예약의 상태 관리

결제하지 않은 예약은 10분 뒤 스케줄러가 자동으로 취소합니다. 그런데 결제 통신 1.5초 사이에 스케줄러가 돌면, PG 승인은 성공했는데 좌석은 이미 회수된 상황이 생길 수 있었습니다.

결제를 시작하면 예약을 `PROCESSING`으로 바꾸고, 스케줄러는 `PENDING`만 보도록 했습니다. 결제가 실패하면 catch에서 `PENDING`으로 되돌립니다.

```
PENDING ──결제 시작──> PROCESSING ──승인 + 저장 성공──> CONFIRMED
   ▲                      │
   └──── 실패 시 복귀 ────┘   (서버가 죽은 경우 5분 뒤 스케줄러가 복구)
```

그런데 PG 통신 중에 서버가 죽거나 재배포되면 catch 자체가 실행되지 않습니다. 이러면 예약은 `PROCESSING`에 영원히 남습니다. 취소는 `PROCESSING`이라 거부되고, 스케줄러는 `PENDING`만 보니 좌석이 계속 묶입니다.

- 결제 시작 시각을 `processing_started_at` 컬럼(Flyway V5)에 기록합니다.
- 스케줄러가 1분마다 결제 시작 후 5분이 지난 `PROCESSING` 예약을 `PENDING`으로 되돌립니다. 그러면 다시 결제하거나 기존 자동 만료로 정리됩니다.

예약 시각(`reserved_at`)을 기준으로 쓰지 않은 이유가 있습니다. 예약하고 9분 뒤에 결제를 시작한 건은 아직 진행 중인데, 예약 시각 기준이면 이걸 잘못 되돌릴 수 있습니다.

한계도 있습니다. 실제 PG라면 되돌리기 전에 PG 거래 조회로 정말 승인이 안 됐는지 확인해야 합니다. 지금은 시뮬레이션이라 결제 기록이 없으면 승인되지 않은 것으로 봅니다.

## 5. 결제와 취소가 동시에 들어올 때

같은 예약에 결제 승인과 취소가 거의 동시에 들어오면, 락이 없는 상태에서는 서로의 변경을 덮어썼습니다. 그 결과 "결제는 완료됐는데 좌석은 반환된" 상태가 생겼습니다. 락을 뺀 상태에서 동시 실행 테스트를 돌리면 5번 연속으로 재현됐습니다.

- 예약을 조회할 때도 비관적 락을 걸어 승인과 취소가 순서대로 처리되게 했습니다.
- 취소할 때 소유자를 확인하기 전에 PG 환불 통신이 먼저 나가는 순서 문제도 있었습니다. 남의 예약 id로 취소를 요청하면 403이 나기 전에 환불 요청부터 나갔던 겁니다. 소유자 확인을 맨 앞으로 옮겼습니다.

적용 후에는 같은 테스트(`ReservationCancelApproveRaceTest`)에서 재현되지 않습니다.

## 6. 로그인 보안

- **계정 존재 여부 노출**: "없는 아이디"와 "틀린 비밀번호"의 에러 메시지가 달랐습니다. 메시지는 하나로 합쳤습니다. 응답 시간도 달랐는데, 아이디가 없으면 BCrypt 비교를 건너뛰어 응답이 더 빨랐기 때문입니다. 그래서 계정이 없어도 더미 해시로 같은 BCrypt 비교를 하게 했습니다.
- **남의 계정 잠그기**: 처음엔 아이디 기준으로 5회 실패하면 잠갔습니다. 그러면 남의 아이디로 일부러 틀리기만 해도 그 사람이 로그인을 못 합니다. 그래서 잠금 기준을 (아이디, IP)로 바꿨습니다.
- **그런데 IP가 전부 같았던 문제**: 운영에서는 모든 요청이 nginx를 거쳐서 들어와 `getRemoteAddr()`가 항상 nginx 컨테이너 IP였습니다. 결국 IP 기준이 무의미했습니다. `server.forward-headers-strategy: native`를 설정해 Tomcat이 `X-Forwarded-For`에서 실제 IP를 꺼내게 했습니다. 이 설정은 내부망(도커 네트워크)에서 온 헤더만 믿고, 오른쪽부터 처음 나오는 외부 IP를 씁니다. 그래서 클라이언트가 헤더에 가짜 IP를 끼워 넣어도 무시됩니다. 실제 Tomcat을 띄우는 테스트(`LoginLockClientIpTest`)로 확인했습니다.

잠금 기록은 서버 메모리에 있어서 재시작하면 초기화되고, 서버를 여러 대로 늘리면 공유되지 않습니다. 여러 IP로 나눠서 시도하는 공격도 이 방식으로는 막지 못합니다.

## 7. N+1 쿼리

공연의 회차 목록을 조회할 때 회차마다 공연과 공연장을 따로 조회하는 쿼리가 나가고 있었습니다. 연관관계는 지연 로딩을 기본으로 두고, 회차 목록처럼 함께 필요한 곳에서만 페치 조인을 써서 쿼리 1번으로 가져오게 했습니다. 컬렉션 조회에는 `default_batch_fetch_size`를 설정해 IN 절로 묶어서 가져옵니다.

## 8. 공연 기간 밖의 회차

KOPIS 목록 응답에는 공연 기간(`prfpdfrom`, `prfpdto`)과 공연장명(`fcltynm`)이 들어 있었는데, 받기만 하고 저장하지 않았습니다. 그래서 관리자가 11월 7일~14일 공연에 11월 21일 회차를 등록해도 막을 방법이 없었습니다.

- 공연 기간과 공연장명 컬럼을 추가했습니다(Flyway V7). KOPIS 날짜는 `2026.11.07` 형식이라 직접 파싱하고, 형식이 다르거나 비어 있으면 기간을 모르는 것으로 보고 비워 둡니다.
- 회차를 등록할 때 날짜가 기간 밖이면 400으로 거절합니다. 첫날과 마지막 날은 시각과 관계없이 허용하고, 기간을 모르는 공연은 예전처럼 검사하지 않습니다.
- 관리자 화면의 날짜 입력에도 기간을 `min`/`max`로 걸었습니다. 다만 화면 제한은 편의용이고, 실제로 막는 건 서버입니다.

**이미 저장된 공연은 기간이 비어 있었습니다.** 운영 DB에는 공연이 100건 있었고, 동기화는 이미 있는 공연을 건너뛰기 때문에 기간이 채워지지 않습니다. 예전에 포스터 컬럼을 추가할 때 만든 backfill(서버가 뜰 때 비어 있는 공연만 KOPIS 상세로 조회해 채우기)을 넓혀서 포스터·기간·공연장 중 비어 있는 값만 채우게 했습니다. 이미 값이 있는 필드는 덮어쓰지 않습니다.

**KOPIS가 연속 호출을 막고 있었습니다.** 단위 테스트는 KOPIS를 목으로 대체해서 통과했는데, MySQL 8.0 컨테이너에 `prod` 프로필로 띄워 운영 상황(기존 공연 90건, 기간 비어 있음)을 재현해 보니 90건 중 앞 8건만 채워졌습니다. 로그에는 나머지 82건이 0.5초 안에 전부 400으로 찍혀 있었고, 실패한 id를 따로 호출하면 정상 응답이 왔습니다. 간격 없이 연달아 부른 게 원인이었습니다. 100ms 간격이면 전부 성공하는 걸 확인하고, 여유를 두어 상세 조회마다 200ms 간격을 넣었습니다. 다시 재현했을 때 90건 중 88건이 채워졌고, 실패한 2건은 다음 기동 때 다시 시도됩니다. 운영에서도 100건 중 98건이 채워졌습니다.

backfill 테스트를 처음 썼을 때는 값이 채워지지 않아 실패했습니다. 기존 테스트가 `PerformanceSyncService`를 `new`로 직접 만들고 있어서 `@Transactional` 프록시가 없었고, 그래서 엔티티 값을 바꿔도 DB에 반영되지 않았던 겁니다. 운영 코드는 스프링 빈이라 문제가 없었고, 테스트도 스프링 빈을 주입받도록 고쳤습니다.

검증 도입 전에 임의 날짜로 만들어 둔 운영 데모 회차는 모두 기간 밖이었습니다. 기간 안의 공연으로 회차를 새로 등록하고, 예전 회차와 거기 묶인 테스트 예약은 정리했습니다.

## 9. 테스터 피드백 반영

지원 전에 지인들에게 운영 사이트를 써 보게 하고 의견을 받았습니다. 코드와 대조해 실제 버그인 것부터 고쳤습니다.

- **지난 회차도 좌석 선택까지 들어감**: 상세 화면이 시작 시각이 지난 회차도 "선택" 버튼으로 보여 주고, 예매를 막는 건 예약 API뿐이었습니다. 그래서 좌석까지 고른 뒤에야 "공연이 이미 시작되어 예매할 수 없습니다"가 떴습니다. 지난 회차는 화면에서 "마감"으로 표시하고, 서버 검증은 그대로 둡니다.
- **아이디에 공백이 들어감**: `@NotBlank`는 공백**만** 있는 값만 막습니다. "ab cd"처럼 중간에 공백이 있으면 통과했습니다. 가입 요청에 `@Pattern`(영문·숫자)을 추가했습니다. 로그인 요청에는 걸지 않아서, 규칙이 생기기 전에 만든 아이디도 로그인은 됩니다.
- **예매할 수 있는 공연이 목록 뒤쪽에 묻힘**: 목록이 id 순이라 예매중인 공연 5개가 여러 페이지에 흩어져 있었고, 끝난 공연도 회차가 없으면 "오픈예정"으로 보였습니다.

목록 정렬은 공연마다 "아직 시작하지 않은 회차가 있는지"를 봐야 해서, 정렬 기준이 회차 테이블에 있습니다. 파생 쿼리와 `Sort`로는 표현이 안 돼서 JPQL로 직접 썼습니다.

```
order by case
  when exists (시작 전 회차) then 0      -- 예매중
  when 종료일이 없거나 오늘 이후 then 1   -- 오픈예정
  else 2                                  -- 공연종료
end, p.id
```

같은 그룹 안에서는 id 순으로 고정해서 '더 보기'로 다음 페이지를 불러올 때 중복이나 누락이 없게 했습니다. 상태 필터(`?status=`)도 같은 `case` 식의 값으로 거르기 때문에, 이 식을 상수로 빼서 정렬·필터·카운트 쿼리가 같은 기준을 쓰게 했습니다. 목록 카드의 배지도 같은 기준입니다.

- 파생 쿼리 `Containing`이 대신 해 주던 `%`, `_` 이스케이프를 직접 처리해야 했습니다. 백슬래시는 Java 텍스트 블록과 DB 문자열에서 각각 해석이 달라 헷갈려서, 이스케이프 문자로 `!`를 썼습니다.
- 상수를 텍스트 블록으로 이어 붙였더니 서버가 뜨지 않았습니다. 텍스트 블록은 줄 끝 공백을 지워서 `or ` 뒤의 공백이 사라졌고, `orcase`라는 토큰이 됐습니다. 이어 붙이는 부분은 일반 문자열로 바꿨습니다.
- 테스트는 H2에서 돌기 때문에, 운영과 같은 MySQL 8.0 컨테이너에 `prod` 프로필로 띄워 정렬·필터·이스케이프를 따로 확인했습니다.

## 10. KOPIS 키가 잘못돼도 "성공"

옛 API 키로 동기화를 돌렸을 때 화면에 제목도 포스터도 없는 공연이 1건 생겼습니다. 동기화 API는 성공 메시지를 그대로 돌려줬습니다.

KOPIS는 키가 등록되지 않았을 때도 HTTP 200을 주고, 정상 응답과 똑같은 `<dbs><db>` 구조 안에 `returncode`(02)와 `errmsg`(SERVICE KEY IS NOT REGISTERED ERROR)만 담아 보냅니다. 응답 객체에는 이 두 필드가 없어서 JAXB가 그냥 "필드가 전부 비어 있는 공연"으로 읽었습니다. 장르 9개를 돌며 이런 항목이 9건 왔지만, 중복 apiId를 거르는 `Set`이 null을 하나로 취급해서 1건만 저장됐습니다.

- 응답 객체에 `returncode`, `errmsg`를 추가하고, 값이 있으면 공연이 아니라 에러로 봅니다. 목록 조회는 빈 리스트, 상세 조회는 null을 돌려주고 에러 메시지를 로그로 남깁니다.
- 다른 형식의 실패가 와도 빈 공연이 쌓이지 않도록, 저장 직전에 apiId나 제목이 빈 항목은 건너뜁니다.
- 테스트는 실제 KOPIS에서 받은 에러 XML을 그대로 돌려주는 로컬 HTTP 서버(JDK `HttpServer`)로 작성했습니다. 고치기 전 코드에서는 이 테스트가 실패하는 것을 확인했습니다.
- 잘못된 키로 서버를 띄워 보면 장르마다 에러 로그가 남고 공연은 0건입니다. 정상 키로는 90건이 들어옵니다.

참고로 KOPIS는 curl 기본 User-Agent로 보낸 요청을 "Request Blocked" HTML 페이지로 막아서, 응답을 직접 확인할 때는 User-Agent를 바꿔야 했습니다.
