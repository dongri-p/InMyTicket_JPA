# 고민했던 문제들 (자세히)

[README로 돌아가기](../README.md)

## 1. 같은 좌석 동시 예매

인기 공연은 남은 좌석 하나에 여러 명이 동시에 예매를 누릅니다. 처음 구현에서는 "좌석이 비었는지 확인 → 예약 처리"가 두 단계로 나뉘어 있었습니다. 그래서 두 요청이 동시에 "비어 있음"을 보고 둘 다 예약에 성공할 수 있었습니다.

- 좌석을 조회할 때 비관적 락(`@Lock(PESSIMISTIC_WRITE)`)을 걸어, 먼저 락을 잡은 요청이 끝날 때까지 다른 요청은 기다리게 했습니다. 기다렸다가 들어온 요청은 이미 예약된 좌석이라 실패합니다.
- 회차의 잔여석 수는 좌석과 성격이 달라서 락을 잡지 않고 `UPDATE ... SET available = available - 1` 같은 원자적 UPDATE로 처리했습니다.
- 여러 좌석 예매(최대 4석)나 취소처럼 좌석 여러 개를 한 번에 잠글 때는 항상 id 순서로 잠가서, 두 트랜잭션이 서로의 락을 기다리는 데드락을 피했습니다.

`ExecutorService`와 `CountDownLatch`로 한 좌석에 예매 요청 100개를 동시에 보내는 테스트(`ReservationServiceTest`)를 만들었고, 성공은 항상 1건입니다.

처음엔 이 테스트를 H2(TCP 모드)에서만 돌렸습니다. MySQL과 H2는 락 동작이 다를 수 있어서, 로컬 Docker의 MySQL 8.0에 직접 연결해 다시 돌렸고 5번 반복해도 성공은 1건, 실패는 99건으로 같았습니다. CI에서는 아직 H2로 돌아서, Testcontainers로 CI에서도 MySQL 기준으로 돌리는 게 다음 과제입니다.

좌석 엔티티에는 `@Version`도 붙어 있습니다. 비관적 락을 거치지 않는 수정 경로가 생기면 그걸 잡아내려는 목적이었습니다. 그런데 지금 코드에서 좌석 상태를 바꾸는 곳은 모두 비관적 락을 거칩니다. 그래서 현재는 실제로 동작할 일이 없는 안전장치에 가깝습니다.

## 2. 결제 통신 동안 DB 커넥션을 붙잡고 있는 문제

결제는 "PG에 승인 요청 → 결과를 DB에 저장" 순서입니다. 처음엔 이걸 `@Transactional` 메서드 하나에 넣었습니다. 그러면 PG 응답을 기다리는 1.5초 동안 DB 커넥션을 계속 쥐고 있게 됩니다. 커넥션 풀은 기본 10개라서, 결제가 몰리면 결제와 상관없는 조회 API까지 커넥션을 못 받고 대기하게 됩니다.

- `PaymentService`: 트랜잭션 없이 PG 통신만 담당합니다.
- `PaymentApprovalService`: PG 승인이 끝난 뒤 결제 저장과 예약 확정만 짧은 트랜잭션으로 처리합니다.

`ConnectionHoldTimeMeasurementTest`에서 실제 HikariPool로 결제 1건당 커넥션 점유 시간을 쟀습니다. 운영과 같은 MySQL 8.0(로컬 Docker)에 연결해서 측정했습니다.

| | 커넥션 점유 시간 |
| --- | --- |
| 트랜잭션 안에서 PG 통신 (개선 전) | 1,526.7ms |
| 트랜잭션 분리 (현재) | 10.8ms (약 141배 감소) |

처음 H2에서 쟀을 때는 개선 전 약 1,517ms, 개선 후 3~4ms였습니다.

다만 이 측정은 서비스를 직접 호출한 값입니다. 실제 HTTP 요청에서는 OSIV가 켜져 있어서 요청 내내 커넥션을 붙잡고 있었고, OSIV를 끈 뒤에야 이 개선이 운영에도 적용됐습니다(6번 참고).

단건 측정이라 "동시에 몇 건까지 버티는지"는 아직 보여주지 못합니다. k6로 동시 결제 상황에서 대기 시간과 실패율을 비교해보려고 합니다.

## 3. PG 승인은 됐는데 DB 저장이 실패하면?

2번처럼 트랜잭션을 나누면, PG 승인과 DB 저장을 하나로 묶어 롤백할 수 없습니다. 승인 후 DB 저장이 실패하면 고객 돈은 빠져나갔는데 결제 기록은 없는 상태가 됩니다.

그래서 `processPayment()`를 두 단계로 나눴습니다.

1. PG 승인이 실패하면: 빠져나간 돈이 없으니 예약만 `PENDING`으로 되돌립니다.
2. PG 승인 후 DB 저장이 실패하면: PG에 승인 취소를 먼저 보내고(보상), 그다음 `PENDING`으로 되돌립니다.

보상을 넣으면서 두 가지를 더 챙겼습니다.

- 보상 요청마저 실패할 수 있습니다. 이때 원래 실패 원인이 가려지지 않게 그대로 던지고, "수동 환불이 필요하다"는 에러 로그와 결제 키를 남깁니다.
- 이미 다른 결제에 쓰인 결제 키로 요청이 들어오면 unique 제약 때문에 DB 저장이 실패합니다. 이때 그 키로 승인 취소를 보내면 다른 사람의 정상 결제가 환불됩니다. 그래서 DB에 이미 기록된 키면 보상을 건너뜁니다. 실제 PG라면 이미 처리된 키는 PG 쪽에서 거절할 테지만, 시뮬레이션 PG는 그렇지 않아서 서버에서 막았습니다.

이 경우들은 실제 DB로 재현하기 어려워서 PG 클라이언트(`PgClient`)를 목으로 바꾼 단위 테스트(`PaymentServiceCompensationTest`)로 확인했습니다.

## 4. 결제 중인 예약의 상태 관리

결제하지 않은 예약은 10분 뒤 스케줄러가 자동으로 취소합니다. 그런데 결제 통신 1.5초 사이에 스케줄러가 돌면, PG 승인은 성공했는데 좌석은 이미 회수된 상황이 생길 수 있었습니다.

결제를 시작하면 예약을 `PROCESSING`으로 바꾸고, 스케줄러는 `PENDING`만 보도록 했습니다. 결제가 실패하면 catch에서 `PENDING`으로 되돌립니다.

```
PENDING ──결제 시작──> PROCESSING ──승인 + 저장 성공──> CONFIRMED
   ▲                      │
   └──── 실패 시 복귀 ────┘   (서버가 죽은 경우 5분 뒤 스케줄러가 복구)
```

그런데 PG 통신 중에 서버가 죽거나 재배포되면 catch 자체가 실행되지 않습니다. 이러면 예약은 `PROCESSING`에 영원히 남습니다. 취소는 `PROCESSING`이라 거부되고, 스케줄러는 `PENDING`만 보니 좌석이 계속 묶입니다.

- 결제 시작 시각을 `processing_started_at` 컬럼(Flyway V5)에 기록합니다.
- 스케줄러가 1분마다 결제 시작 후 5분이 지난 `PROCESSING` 예약을 `PENDING`으로 되돌립니다. 그러면 다시 결제하거나 기존 자동 만료로 정리됩니다.

예약 시각(`reserved_at`)을 기준으로 쓰지 않은 이유가 있습니다. 예약하고 9분 뒤에 결제를 시작한 건은 아직 진행 중인데, 예약 시각 기준이면 이걸 잘못 되돌릴 수 있습니다.

한계도 있습니다. 실제 PG라면 되돌리기 전에 PG 거래 조회로 정말 승인이 안 됐는지 확인해야 합니다. 지금은 시뮬레이션이라 결제 기록이 없으면 승인되지 않은 것으로 봅니다.

## 5. 결제와 취소가 동시에 들어올 때

같은 예약에 결제 승인과 취소가 거의 동시에 들어오면, 락이 없는 상태에서는 서로의 변경을 덮어썼습니다. 그 결과 "결제는 완료됐는데 좌석은 반환된" 상태가 생겼습니다. 락을 뺀 상태에서 동시 실행 테스트를 돌리면 5번 연속으로 재현됐습니다.

- 예약을 조회할 때도 비관적 락을 걸어 승인과 취소가 순서대로 처리되게 했습니다.
- 취소할 때 소유자를 확인하기 전에 PG 환불 통신이 먼저 나가는 순서 문제도 있었습니다. 남의 예약 id로 취소를 요청하면 403이 나기 전에 환불 요청부터 나갔던 겁니다. 소유자 확인을 맨 앞으로 옮겼습니다.

적용 후에는 같은 테스트(`ReservationCancelApproveRaceTest`)에서 재현되지 않습니다.

## 6. 락을 걸고 다시 읽었는데 옛날 값이 나오는 문제

외부 기술 피드백에서 지적받은 문제입니다. 4·5번에서 "락을 잡은 뒤 상태를 다시 확인한다"는 방어 코드를 넣었는데, 이 재확인이 실제로는 최신 상태를 보지 못하는 경우가 있었습니다.

### 자동 만료 스케줄러

스케줄러는 락 없이 오래된 `PENDING` 예약을 찾고, 그 예약들에 락을 건 뒤 상태를 다시 확인해서 아직 `PENDING`인 것만 취소합니다. 문제는 처음 찾을 때 예약을 엔티티로 조회했다는 점입니다.

| 순서 | 스케줄러 (트랜잭션 1) | 결제 요청 (트랜잭션 2) |
| --- | --- | --- |
| 1 | 후보 조회 → 예약이 `PENDING`으로 영속성 컨텍스트에 올라감 | |
| 2 | | 결제 승인 → `CONFIRMED`로 바꾸고 커밋 |
| 3 | 락을 걸고 다시 조회 → DB에서는 `CONFIRMED`를 읽어옴 | |
| 4 | 그런데 반환된 엔티티는 여전히 `PENDING` → 예약 취소, 좌석 회수 | |

3번에서 `SELECT ... FOR UPDATE`는 실제로 DB에 나가고 최신 행도 읽어옵니다. 하지만 JPA는 같은 영속성 컨텍스트에 이미 있는 엔티티를 다시 읽으면, 새로 읽은 값으로 덮어쓰지 않고 원래 있던 객체를 돌려줍니다. 그래서 결제가 끝난 예약을 취소하고 좌석을 다른 사람에게 다시 팔 수 있었습니다. 좌석의 `@Version`도 도움이 안 됐습니다. 결제는 좌석을 바꾸지 않아서 좌석 버전은 그대로였기 때문입니다.

트랜잭션 하나 안에서 "후보 조회 → 다른 트랜잭션(`REQUIRES_NEW`)이 결제 승인 → 락 조회" 순서를 그대로 만든 테스트로 먼저 재현했습니다. 결과는 `expected: <CONFIRMED> but was: <PENDING>`였습니다.

후보는 엔티티 대신 id만 조회하도록 바꿨습니다(`select r.id from Reservation r ...`). id만 받으면 영속성 컨텍스트에 엔티티가 올라가지 않으니, 락을 거는 조회에서 엔티티가 처음 로딩되어 항상 최신 상태를 봅니다. `PROCESSING` 고착 복구 스케줄러도 같은 구조라 똑같이 고쳤습니다. 엔티티를 `refresh()`로 다시 읽는 방법도 있지만, 후보가 여러 건이면 건마다 쿼리가 나가서 id 조회를 골랐습니다.

### 취소 API와 OSIV

취소는 "환불할 결제가 있는지 확인(트랜잭션 A) → PG 환불 → 락을 걸고 취소(트랜잭션 B)" 순서입니다. A와 B 사이에 결제가 끝나면, B에서 "확인할 땐 없던 결제가 생겼으니 다시 시도하라"고 거부하도록 만들어 두었습니다.

그런데 OSIV(`spring.jpa.open-in-view`)가 기본값(켜짐) 그대로였습니다. OSIV가 켜져 있으면 트랜잭션을 나눠도 HTTP 요청 하나 동안 영속성 컨텍스트를 같이 씁니다. 그래서 B의 락 조회가 A에서 읽어둔 "결제 없음" 엔티티를 그대로 받았고, 이 거부 로직이 동작하지 않았습니다. 결제된 예약이 환불 없이 취소된 겁니다.

실제 취소 API를 호출하면서 A가 끝난 직후 다른 스레드에서 결제를 완료시키는 테스트(`CancelPaymentRaceOverHttpTest`)로 재현했습니다. 수정 전에는 200 "예매가 취소되었습니다"가 나왔습니다. `open-in-view: false`로 끈 뒤에는 취소가 거부되고 예약은 `CONFIRMED`로 남습니다.

### OSIV가 2번의 개선도 막고 있었음

OSIV는 요청이 끝날 때까지 DB 커넥션도 붙잡고 있습니다. 2번에서 PG 통신을 트랜잭션 밖으로 뺐지만, 실제 HTTP 요청에서는 이 효과가 없었던 겁니다. 2번의 측정은 서비스를 직접 호출해서 잰 값이라 OSIV가 끼어들지 않았습니다.

결제 API를 실제로 호출하면서 커넥션 풀의 active 커넥션을 재봤습니다(데모 PG 1.5초, H2).

| | HTTP 결제 요청 시간 | 커넥션 점유 시간 |
| --- | --- | --- |
| OSIV 켜짐 (수정 전) | 약 1,522ms | 약 1,517ms |
| OSIV 꺼짐 (현재) | 약 1,514ms | 15ms 이하 |

이 측정은 테스트(`PaymentConnectionHoldOverHttpTest`)로 남겨 두었습니다. OSIV를 다시 켜면 이 테스트가 실패합니다.

OSIV를 끄면 트랜잭션 밖(컨트롤러)에서 지연 로딩을 할 수 없습니다. 전체 테스트를 돌리고, 로컬에서 공연 목록·상세·회차·좌석·예매·내 예매·취소 API를 하나씩 호출해서 지연 로딩 오류가 없는지 확인했습니다.

배운 점은 "락을 걸고 다시 조회했으니 최신이다"가 JPA에서는 당연하지 않다는 것입니다. 같은 영속성 컨텍스트에서는 다시 조회해도 엔티티가 바뀌지 않습니다. 그리고 영속성 컨텍스트가 어디까지 이어지는지는 트랜잭션만 보고 판단하면 안 되고, OSIV 설정까지 봐야 합니다.

## 7. 로그인 보안

- **계정 존재 여부 노출**: "없는 아이디"와 "틀린 비밀번호"의 에러 메시지가 달랐습니다. 메시지는 하나로 합쳤습니다. 응답 시간도 달랐는데, 아이디가 없으면 BCrypt 비교를 건너뛰어 응답이 더 빨랐기 때문입니다. 그래서 계정이 없어도 더미 해시로 같은 BCrypt 비교를 하게 했습니다.
- **남의 계정 잠그기**: 처음엔 아이디 기준으로 5회 실패하면 잠갔습니다. 그러면 남의 아이디로 일부러 틀리기만 해도 그 사람이 로그인을 못 합니다. 그래서 잠금 기준을 (아이디, IP)로 바꿨습니다.
- **그런데 IP가 전부 같았던 문제**: 운영에서는 모든 요청이 nginx를 거쳐서 들어와 `getRemoteAddr()`가 항상 nginx 컨테이너 IP였습니다. 결국 IP 기준이 무의미했습니다. `server.forward-headers-strategy: native`를 설정해 Tomcat이 `X-Forwarded-For`에서 실제 IP를 꺼내게 했습니다. 이 설정은 내부망(도커 네트워크)에서 온 헤더만 믿고, 오른쪽부터 처음 나오는 외부 IP를 씁니다. 그래서 클라이언트가 헤더에 가짜 IP를 끼워 넣어도 무시됩니다. 실제 Tomcat을 띄우는 테스트(`LoginLockClientIpTest`)로 확인했습니다.

잠금 기록은 서버 메모리에 있어서 재시작하면 초기화되고, 서버를 여러 대로 늘리면 공유되지 않습니다. 여러 IP로 나눠서 시도하는 공격도 이 방식으로는 막지 못합니다.

## 8. N+1 쿼리

공연의 회차 목록을 조회할 때 회차마다 공연과 공연장을 따로 조회하는 쿼리가 나가고 있었습니다. 연관관계는 지연 로딩을 기본으로 두고, 회차 목록처럼 함께 필요한 곳에서만 페치 조인을 써서 쿼리 1번으로 가져오게 했습니다. 컬렉션 조회에는 `default_batch_fetch_size`를 설정해 IN 절로 묶어서 가져옵니다.

## 9. 공연 기간 밖의 회차

KOPIS 목록 응답에는 공연 기간(`prfpdfrom`, `prfpdto`)과 공연장명(`fcltynm`)이 들어 있었는데, 받기만 하고 저장하지 않았습니다. 그래서 관리자가 11월 7일~14일 공연에 11월 21일 회차를 등록해도 막을 방법이 없었습니다.

- 공연 기간과 공연장명 컬럼을 추가했습니다(Flyway V7). KOPIS 날짜는 `2026.11.07` 형식이라 직접 파싱하고, 형식이 다르거나 비어 있으면 기간을 모르는 것으로 보고 비워 둡니다.
- 회차를 등록할 때 날짜가 기간 밖이면 400으로 거절합니다. 첫날과 마지막 날은 시각과 관계없이 허용하고, 기간을 모르는 공연은 예전처럼 검사하지 않습니다.
- 관리자 화면의 날짜 입력에도 기간을 `min`/`max`로 걸었습니다. 다만 화면 제한은 편의용이고, 실제로 막는 건 서버입니다.

**이미 저장된 공연은 기간이 비어 있었습니다.** 운영 DB에는 공연이 100건 있었고, 동기화는 이미 있는 공연을 건너뛰기 때문에 기간이 채워지지 않습니다. 예전에 포스터 컬럼을 추가할 때 만든 backfill(서버가 뜰 때 비어 있는 공연만 KOPIS 상세로 조회해 채우기)을 넓혀서 포스터·기간·공연장 중 비어 있는 값만 채우게 했습니다. 이미 값이 있는 필드는 덮어쓰지 않습니다.

**KOPIS가 연속 호출을 막고 있었습니다.** 단위 테스트는 KOPIS를 목으로 대체해서 통과했는데, MySQL 8.0 컨테이너에 `prod` 프로필로 띄워 운영 상황(기존 공연 90건, 기간 비어 있음)을 재현해 보니 90건 중 앞 8건만 채워졌습니다. 로그에는 나머지 82건이 0.5초 안에 전부 400으로 찍혀 있었고, 실패한 id를 따로 호출하면 정상 응답이 왔습니다. 간격 없이 연달아 부른 게 원인이었습니다. 100ms 간격이면 전부 성공하는 걸 확인하고, 여유를 두어 상세 조회마다 200ms 간격을 넣었습니다. 다시 재현했을 때 90건 중 88건이 채워졌고, 실패한 2건은 다음 기동 때 다시 시도됩니다. 운영에서도 100건 중 98건이 채워졌습니다.

backfill 테스트를 처음 썼을 때는 값이 채워지지 않아 실패했습니다. 기존 테스트가 `PerformanceSyncService`를 `new`로 직접 만들고 있어서 `@Transactional` 프록시가 없었고, 그래서 엔티티 값을 바꿔도 DB에 반영되지 않았던 겁니다. 운영 코드는 스프링 빈이라 문제가 없었고, 테스트도 스프링 빈을 주입받도록 고쳤습니다.

검증 도입 전에 임의 날짜로 만들어 둔 운영 데모 회차는 모두 기간 밖이었습니다. 기간 안의 공연으로 회차를 새로 등록하고, 예전 회차와 거기 묶인 테스트 예약은 정리했습니다.

## 10. 테스터 피드백 반영

지원 전에 지인들에게 운영 사이트를 써 보게 하고 의견을 받았습니다. 코드와 대조해 실제 버그인 것부터 고쳤습니다.

- **지난 회차도 좌석 선택까지 들어감**: 상세 화면이 시작 시각이 지난 회차도 "선택" 버튼으로 보여 주고, 예매를 막는 건 예약 API뿐이었습니다. 그래서 좌석까지 고른 뒤에야 "공연이 이미 시작되어 예매할 수 없습니다"가 떴습니다. 지난 회차는 화면에서 "마감"으로 표시하고, 서버 검증은 그대로 둡니다.
- **아이디에 공백이 들어감**: `@NotBlank`는 공백**만** 있는 값만 막습니다. "ab cd"처럼 중간에 공백이 있으면 통과했습니다. 가입 요청에 `@Pattern`(영문·숫자)을 추가했습니다. 로그인 요청에는 걸지 않아서, 규칙이 생기기 전에 만든 아이디도 로그인은 됩니다.
- **예매할 수 있는 공연이 목록 뒤쪽에 묻힘**: 목록이 id 순이라 예매중인 공연 5개가 여러 페이지에 흩어져 있었고, 끝난 공연도 회차가 없으면 "오픈예정"으로 보였습니다.

목록 정렬은 공연마다 "아직 시작하지 않은 회차가 있는지"를 봐야 해서, 정렬 기준이 회차 테이블에 있습니다. 파생 쿼리와 `Sort`로는 표현이 안 돼서 JPQL로 직접 썼습니다.

```
order by case
  when exists (시작 전 회차) then 0      -- 예매중
  when 종료일이 없거나 오늘 이후 then 1   -- 오픈예정
  else 2                                  -- 공연종료
end, p.id
```

같은 그룹 안에서는 id 순으로 고정해서 '더 보기'로 다음 페이지를 불러올 때 순서가 흔들리지 않게 했습니다(이후 12번에서 OFFSET 대신 커서로 바꿨습니다). 상태 필터(`?status=`)도 같은 `case` 식의 값으로 거르기 때문에, 이 식을 상수로 빼서 정렬·필터·카운트 쿼리가 같은 기준을 쓰게 했습니다. 목록 카드의 배지도 같은 기준입니다.

- 파생 쿼리 `Containing`이 대신 해 주던 `%`, `_` 이스케이프를 직접 처리해야 했습니다. 백슬래시는 Java 텍스트 블록과 DB 문자열에서 각각 해석이 달라 헷갈려서, 이스케이프 문자로 `!`를 썼습니다.
- 상수를 텍스트 블록으로 이어 붙였더니 서버가 뜨지 않았습니다. 텍스트 블록은 줄 끝 공백을 지워서 `or ` 뒤의 공백이 사라졌고, `orcase`라는 토큰이 됐습니다. 이어 붙이는 부분은 일반 문자열로 바꿨습니다.
- 테스트는 H2에서 돌기 때문에, 운영과 같은 MySQL 8.0 컨테이너에 `prod` 프로필로 띄워 정렬·필터·이스케이프를 따로 확인했습니다.

## 11. KOPIS 키가 잘못돼도 "성공"

옛 API 키로 동기화를 돌렸을 때 화면에 제목도 포스터도 없는 공연이 1건 생겼습니다. 동기화 API는 성공 메시지를 그대로 돌려줬습니다.

KOPIS는 키가 등록되지 않았을 때도 HTTP 200을 주고, 정상 응답과 똑같은 `<dbs><db>` 구조 안에 `returncode`(02)와 `errmsg`(SERVICE KEY IS NOT REGISTERED ERROR)만 담아 보냅니다. 응답 객체에는 이 두 필드가 없어서 JAXB가 그냥 "필드가 전부 비어 있는 공연"으로 읽었습니다. 장르 9개를 돌며 이런 항목이 9건 왔지만, 중복 apiId를 거르는 `Set`이 null을 하나로 취급해서 1건만 저장됐습니다.

- 응답 객체에 `returncode`, `errmsg`를 추가하고, 값이 있으면 공연이 아니라 에러로 봅니다. 목록 조회는 빈 리스트, 상세 조회는 null을 돌려주고 에러 메시지를 로그로 남깁니다.
- 다른 형식의 실패가 와도 빈 공연이 쌓이지 않도록, 저장 직전에 apiId나 제목이 빈 항목은 건너뜁니다.
- 테스트는 실제 KOPIS에서 받은 에러 XML을 그대로 돌려주는 로컬 HTTP 서버(JDK `HttpServer`)로 작성했습니다. 고치기 전 코드에서는 이 테스트가 실패하는 것을 확인했습니다.
- 잘못된 키로 서버를 띄워 보면 장르마다 에러 로그가 남고 공연은 0건입니다. 정상 키로는 90건이 들어옵니다.

참고로 KOPIS는 curl 기본 User-Agent로 보낸 요청을 "Request Blocked" HTML 페이지로 막아서, 응답을 직접 확인할 때는 User-Agent를 바꿔야 했습니다.

## 12. API 응답 규칙이 제각각이던 문제

외부 기술 피드백에서 "REST API 응답이 일관되지 않다"는 지적을 받았습니다. 코드를 다시 보니 같은 서버 안에서 규칙이 여러 개였습니다.

### 예매 상태 기준이 세 군데

- 응답의 `status`는 KOPIS가 준 한글 값("공연예정")
- 목록 필터 `?status=`는 서버가 계산한 `ON_SALE / UPCOMING / ENDED`
- 목록 배지는 프론트가 회차 수와 종료일로 따로 계산, 상세 배지는 KOPIS 한글 값

실제로 회차가 열려 있는 공연이 상세 화면에선 "공연예정"으로 보였습니다. 판정을 `BookingStatus.of(회차 수, 종료일, 오늘)` 하나로 모으고 응답에 `bookingStatus`로 내려서, 필터·정렬·배지가 모두 같은 값을 쓰게 했습니다. 정렬·필터는 JPQL `case` 식이고 응답은 Java라서, 두 규칙이 어긋나지 않는지 "필터로 고른 공연의 `bookingStatus`가 필터 값과 같은지" 테스트로 묶어 두었습니다. 배포 순서 때문에 프론트가 새 값을 쓰도록 먼저 바꾼 뒤 KOPIS `status`는 응답에서 뺐습니다.

### 상태 코드와 응답 본문

| | 전 | 후 |
| --- | --- | --- |
| 생성 (회원가입·공연장·회차·예매·결제) | 200 `{id, message}` | 201 + `Location` + `{id}` |
| 예매 취소 | `DELETE /reservations/{id}` 200 `{message}` | `POST /reservations/{id}/cancel` 204 |
| KOPIS 동기화 | 200 문자열 | 204 |
| URL의 공연·회차·예약이 없음 | 400 | 404 |
| 없는 경로, 지원하지 않는 메서드 | 500 | 404, 405 |

- 안내 문구(`message`)는 화면에서 정하는 게 맞다고 보고 응답에서 뺐습니다. 서버는 무슨 일이 일어났는지를 상태 코드로 알려줍니다.
- 취소는 예약 행을 지우지 않고 `CANCELLED`로 바꾸고 결제 건은 환불까지 하는 상태 변경이라, `DELETE`보다 취소 동작 URL이 의미에 맞았습니다. 이미 취소된 예약을 다시 취소하면 409입니다.
- 404와 400은 "URL이 가리키는 대상이 없으면 404, 요청 본문에 담긴 id가 틀리면 400"으로 나눴습니다. 없는 좌석으로 예매하는 건 찾는 대상이 없는 게 아니라 요청 내용이 틀린 것이라 400입니다. 404용 예외(`ResourceNotFoundException`)는 `OwnershipViolationException`처럼 스프링에 의존하지 않는 도메인 예외로 두었습니다.
- `Location`을 붙이고 보니 그 주소로 갈 단건 조회 API가 하나도 없었습니다. 응답이 가리키는 주소가 404라 헤더만 형식을 맞춘 셈이어서, 회원·공연장·회차·예매·결제에 단건 조회를 추가했습니다. 예매·결제·회원은 본인 것만(다른 회원이면 403), 공연장은 관리자만 볼 수 있습니다. 테스트는 생성 응답의 `Location`을 그대로 GET 해서 방금 만든 리소스가 나오는지 확인합니다.
- 마지막 `Exception` 핸들러가 스프링의 "경로 없음", "메서드 없음" 예외까지 잡아서 500으로 바꾸고 있었습니다. 옛 `DELETE` 취소 URL로 요청해 보다가 발견했습니다.
- 바꾸면서 테스트 하나가 헛통과할 뻔했습니다. "취소 도중 결제가 끝나면 취소가 거부된다"는 테스트가 응답이 200이 아닌지만 보고 있었는데, 취소 성공이 204가 되면 버그가 다시 생겨도 통과합니다. 2xx가 아닌지를 보도록 고쳤습니다.

### '더 보기'인데 OFFSET

목록은 "더 보기" 버튼으로 이어 붙이는데 서버는 `page`(OFFSET)로 읽고 있었습니다. 첫 페이지를 본 사이 앞쪽에 공연이 하나 생기면, 다음 페이지 첫 줄에 이미 본 공연이 다시 나옵니다(삭제되면 하나를 건너뜁니다). 뒤 페이지로 갈수록 건너뛸 행도 늘어납니다.

직전 페이지 마지막 공연의 정렬 키 `(예매 상태 그룹, id)`를 커서로 주고, 다음 요청은 그 뒤만 읽게 바꿨습니다.

```
where ... and (그룹 > 커서 그룹 or (그룹 = 커서 그룹 and id > 커서 id))
order by 그룹, id
limit size + 1
```

- `size + 1`건을 읽어서 남는 게 있으면 `nextCursor`를 줍니다. 그래서 매 요청마다 전체 건수를 셀 필요가 없고, 건수는 첫 요청에서만 계산합니다.
- 커서는 `그룹:id`를 Base64로 감싼 문자열입니다. 화면은 받은 값을 그대로 돌려줄 뿐 안쪽 구조를 몰라도 됩니다. 형식이 틀리면 400입니다.
- "첫 페이지를 받은 뒤 맨 앞 그룹에 공연이 추가돼도 다음 페이지에 중복이 없다"는 테스트를 넣었습니다. OFFSET이었다면 실패하는 시나리오입니다.
- 정렬 식이 WHERE에도 반복해서 들어가서, 공연 목록 테스트 24개를 운영과 같은 MySQL 8.0 컨테이너에서도 돌려 확인했습니다.

한계도 있었습니다. 정렬 키인 예매 상태 그룹은 회차 테이블을 보는 `case` 식이라 인덱스로 커서 위치를 바로 찾아가지 못합니다. 공연 100건 정도에서는 문제가 없었는데, 데이터를 늘려 보니 실제로 가장 큰 병목이 돼서 13장에서 컬럼으로 바꿨습니다. 또 시간이 지나 예매중이던 공연의 회차가 모두 시작하면 그룹이 바뀌는데, 그 순간 페이지 경계에 걸린 공연은 한 번 중복되거나 빠질 수 있습니다.

### 지역 필터 값

`RegionGroup`(`SEOUL`, `GYEONGGI_INCHEON` …)은 화면의 칩 구성을 그대로 API 값으로 쓴 것입니다. 칩을 "경기"와 "인천"으로 나누면 API 값도 바뀌어야 하고, 옛 값으로 저장된 링크는 400이 됩니다. 권역은 화면 정책이라 서버는 시·도 단위 코드로 받고, 권역으로 묶는 건 화면이나 별도 매핑 테이블이 맡는 게 맞다고 봅니다. 이 부분은 코드는 그대로 두고 한계로 적어 두었습니다.

### 에러 응답에 코드가 없음

에러 응답은 `{status, message}`뿐이었습니다. 같은 409라도 "이미 예매된 좌석"이면 좌석 현황을 새로 보여줘야 하고, "결제 진행 중"이면 잠시 뒤 다시 확인하면 되는데, 화면이 이걸 나누려면 문구를 비교하는 수밖에 없었습니다. 메시지에는 `status=PENDING`, `seatIds=[...]` 같은 내부 값도 섞여 나갔습니다.

- `ErrorCode` enum(코드, HTTP 상태, 사용자 문구)과 `BusinessException` 하나로 규칙 위반을 표현하게 했습니다. 서비스는 "무슨 일이 일어났는지"만 코드로 던지고, HTTP 상태로 바꾸는 건 `GlobalExceptionHandler` 한 곳에서 합니다. `IllegalStateException`/`IllegalArgumentException`과 404·403용 예외 두 개를 이걸로 대체했습니다.
- 응답은 `{status, code, message}`입니다. 인증 필터가 직접 쓰는 401/403 응답도 같은 형태로 맞췄습니다.
- 정리하면서 상태 코드도 바로잡았습니다. 로그인 실패는 400에서 401로, 로그인 시도 제한은 409에서 429(Too Many Requests)로, PG 통신 오류는 502로 바꿨습니다.
- 화면에서는 예매 실패 응답이 `SEAT_ALREADY_RESERVED`면 좌석 목록을 다시 받아, 먼저 팔린 좌석은 회색으로 바꾸고 선택에서 뺍니다. 전에는 "이미 예매 완료된 좌석입니다"라는 문구만 떠서, 두 자리를 골랐을 때 어느 좌석이 빠졌는지 알 수 없었습니다.

### 결제를 다시 요청하면 실패로 보임

결제 승인은 PG 통신(약 1.5초)을 기다려야 해서, 그 사이 네트워크가 끊기거나 사용자가 새로고침하면 클라이언트가 같은 요청을 다시 보낼 수 있습니다. 이때 PG 승인은 이미 끝나 예약이 `CONFIRMED`라서, 재요청은 409 "결제할 수 없는 예약 상태"를 받았습니다. 돈은 빠져나갔는데 화면은 실패로 보이는 상태입니다.

같은 테스트에서 하나를 더 찾았습니다. 이미 쓰인 `paymentKey`로 다른 예약을 결제하면, PG 승인이 먼저 나가고 결제 기록을 저장할 때에야 DB unique 제약에서 막혔습니다. 게다가 "이미 기록된 키면 남의 결제를 환불하지 않도록 보상을 건너뛴다"는 3번의 규칙 때문에 환불도 되지 않았습니다.

- PG를 부르기 전에 `paymentKey`로 기존 결제를 먼저 찾습니다. 같은 예약·같은 금액의 완료된 결제면 PG를 다시 부르지 않고 그 결제 id를 처음과 같은 201로 돌려줍니다. 다른 예약이나 금액에 쓰인 키면 409 `PAYMENT_KEY_REUSED`로 막습니다.
- 첫 요청이 아직 PG 통신 중일 때 겹쳐 들어온 요청은 "결제 불가"가 아니라 409 `PAYMENT_ALREADY_PROCESSING`으로 알려줍니다. 끝난 뒤 다시 보내면 위 규칙대로 같은 결제를 돌려받습니다.
- 멱등성 키를 따로 받는 `Idempotency-Key` 헤더 대신 `paymentKey`를 썼습니다. 토스에서 `paymentKey` 하나가 결제 한 건을 뜻하고, 결제 테이블에 이미 unique로 저장하고 있어서 새 저장소 없이 같은 효과를 낼 수 있었습니다.
- 테스트(`PaymentIdempotencyTest`)는 데모 PG를 스파이로 감싸 승인 호출 횟수를 셉니다. 같은 요청 두 번에 PG 승인 1번·같은 결제 id, 키 재사용 409, 진행 중 409 후 재시도 성공. 고치기 전에는 세 테스트 모두 실패했습니다.

예매 요청에는 아직 멱등성이 없습니다. 같은 예매 요청을 두 번 보내면 두 번째는 자기가 방금 잡은 좌석 때문에 `SEAT_ALREADY_RESERVED`를 받습니다. 화면에서는 요청 중 버튼을 막아 두었지만, API만으로 막으려면 클라이언트가 만든 `Idempotency-Key`를 저장해 두는 장치가 필요합니다.

## 13. 데이터를 늘리자 공연 목록이 다른 API까지 느리게 만든 문제

외부 기술 피드백에서 "데이터가 수백 건이면 성능 문제가 드러나지 않는다, 데이터를 늘리고 p90/p95/p99를 재서 병목을 하나씩 줄여 보라"는 의견을 받았습니다.

### 측정 환경

- 로컬 Docker의 MySQL 8.0(운영과 같은 버전, 버퍼 풀 기본값 128MB)에 별도 DB를 만들고, 앱을 운영 프로필로 띄워 Flyway로 스키마를 만든 뒤 [perf/seed-large-data.sql](../perf/seed-large-data.sql)로 데이터를 넣었습니다(9분).
- 회원 10만 / 공연 10만 / 공연장 40(200~500석) / 회차 1만 / 좌석 350만(VIP·R·S·A) / 예매·티켓 117만 / 결제 93만
- k6 시나리오([perf/k6/browse.js](../perf/k6/browse.js)): 가상 사용자마다 다른 회원으로 로그인해서 공연 목록(절반은 장르+예매 상태 필터) → 상세 → 회차 → 좌석 → 내 예매를 반복합니다. 엔드포인트별로 p50/p90/p95/p99를 따로 봅니다.
- k6·앱·MySQL이 모두 한 PC(16코어)에서 돌아서 운영 서버 수치와는 다릅니다. 같은 조건에서 바꾸기 전·후를 비교하는 용도입니다.

### 처음 측정 (100명, 60초)

| API | p50 | p95 | p99 |
| --- | --- | --- | --- |
| 공연 목록 | 1.53s | 2.73s | 3.14s |
| 공연 목록 + 필터 | 1.48s | 2.86s | 3.21s |
| 공연 상세 | 488ms | 1.11s | 1.52s |
| 회차 | 346ms | 753ms | 1.13s |
| 좌석 | 359ms | 740ms | 1.04s |
| 내 예매 | 373ms | 845ms | 1.21s |

혼자 호출하면 좌석·회차·내 예매는 10~20ms였고 공연 목록만 190ms 정도였습니다. 부하를 걸자 빠르던 API까지 같이 느려진 게 이상해서 목록부터 봤습니다.

### 원인: 20건을 보여주려고 10만 건을 정렬

목록 쿼리를 `EXPLAIN ANALYZE`로 보면 이렇습니다.

```
Limit: 21 row(s)  (actual time=153..153)
  -> Sort: (case when exists(select #2) then 0 ... end), performance_id
    -> Table scan on p  (rows=100000)
-> Select #2 (dependent)  ... loops=100000
  -> Index lookup on schedule using fk_schedule_performance
```

정렬 키인 예매 상태(12장)가 "시작 전 회차가 있는가"를 보는 식이라, 공연 10만 건 각각에 회차 서브쿼리를 돌려 값을 만든 다음에야 정렬하고 21건을 자릅니다. 첫 페이지 한 번에 150ms, 예매 상태 필터로 종료된 공연 뒤쪽 커서를 읽으면 275ms였습니다. 계산식이라 인덱스를 걸 수도 없습니다.

나머지 API가 같이 느려진 건 커넥션 풀(10개) 때문으로 봤습니다. 목록 요청이 커넥션을 150ms씩 잡고 있으니, 1ms짜리 좌석 조회도 커넥션이 날 때까지 기다립니다. 실제로 아래 1번만 고쳤는데 좌석 조회 p95가 740ms에서 250ms로 같이 내려갔습니다.

### 1. 예매 상태를 컬럼으로 저장

`performance`에 `booking_group`(0 예매중 / 1 오픈예정 / 2 공연종료)과 `last_schedule_at`(가장 늦은 회차 시각)을 추가하고 `(booking_group, performance_id)` 인덱스를 걸었습니다(V10). 목록은 계산식 대신 이 컬럼으로 거르고 정렬해서, 인덱스 순서대로 21건만 읽고 끝납니다.

```
Limit: 21 row(s)  (actual time=0.0259..0.117)
  -> Index scan on p using idx_performance_booking_group  (rows=21)
```

문제는 이 값이 시간이 지나면 바뀐다는 점입니다. 바뀌는 경우를 나눠 보니 올라가는 쪽과 내려가는 쪽이 달랐습니다.

- 올라가는 경우(회차 등록 → 예매중)는 사람이 하는 일이라 등록하는 순간 바로 바꿉니다(`Performance.scheduleAdded`).
- 내려가는 경우(마지막 회차 시작 → 오픈예정/종료, 종료일 경과 → 종료)는 아무 요청 없이 시간만 지나서 일어나서, 1분마다 도는 `BookingGroupScheduler`가 UPDATE 두 개로 내립니다. 둘 다 "지금 예매중인 공연", "지금 오픈예정인 공연"만 인덱스로 좁혀서 봅니다.

그래서 목록의 예매 상태는 최대 1분 늦을 수 있습니다. 그 사이 마지막 회차가 시작된 공연이 예매중으로 보여도, 예매할 때 회차 시각을 따로 검사하기 때문에 지난 회차가 팔리지는 않습니다. 목록 배지와 커서도 저장값을 쓰게 해서 정렬과 어긋나지 않게 했고, 상세 화면은 공연 하나라 그대로 실시간으로 계산합니다.

운영에 배포한 뒤 저장된 값과 실제 남은 회차 수로 계산한 값을 공연 100건 전부 비교해 봤고, 어긋난 공연은 없었습니다. 마이그레이션의 `NOW()`는 DB 서버 시간대를 따라서 앱(KST)과 다를 수 있는데, 어긋나도 스케줄러가 1분 안에 바로잡게 되어 있습니다.

결과: 전체 p95 1.84s → 440ms, 처리량 27 → 100회/초

### 2. 장르 필터 건수를 인덱스만으로 세기

목록 쿼리 자체는 0.1ms가 됐는데 목록 API p95는 여전히 575ms였습니다. 첫 페이지마다 같이 나가는 전체 건수 count를 보니, 장르 필터가 붙으면 `booking_group` 인덱스로 그룹 전체(4~5만 건)를 찾은 뒤 행마다 테이블에 가서 장르를 확인하느라 25~36ms가 걸렸습니다.

처음엔 `(category, booking_group)` 인덱스를 따로 만들었는데, 옵티마이저가 이 인덱스를 고르지 않았습니다. `FORCE INDEX`를 주면 35.8ms → 5.3ms로 빨라지는데도 행 수 추정이 틀려서 기존 인덱스를 썼습니다. JPQL에서 힌트를 쓰는 대신 기존 인덱스 끝에 장르를 붙여 `(booking_group, performance_id, category)`로 넓혔습니다(V11). 정렬 순서는 그대로 쓰면서, count는 테이블에 가지 않고 인덱스만 읽습니다(11~17ms).

결과: 전체 p95 440ms → 362ms, 처리량 100 → 118회/초

### 3. 전체 건수는 30초 캐시

여기서 10명과 100명 결과를 비교해 보니, 처리량이 10명일 때 131회/초로 100명(118회/초)보다 오히려 높았습니다. 사람을 늘려도 처리량은 그대로이고 기다리는 시간만 늘어나는, 이미 한계에 닿은 상태였습니다. 이때 MySQL은 CPU 4.25코어를, 앱은 0.79코어를 쓰고 있어서 DB가 병목이었습니다.

`performance_schema`의 쿼리별 누적 시간을 보니 목록 첫 페이지의 전체 건수 count 두 종류가 DB 시간의 약 70%였습니다(필터 있을 때 평균 22.9ms, 없을 때 9.2ms). 목록 쿼리 자체는 순위에도 없었습니다.

건수는 화면에 "N건"으로만 쓰는 값이라 조금 늦어도 괜찮다고 보고, 필터 조합별로 30초 캐시했습니다.

- 검색어가 있는 요청은 경우의 수가 끝이 없어서 캐시하지 않습니다. 장르 6 × 지역 6 × 상태 4로 캐시 키는 최대 144개입니다.
- 캐시를 맞혔을 때 DB 커넥션을 쓰지 않도록, 건수 조회 메서드는 트랜잭션을 열지 않게 했습니다(`Propagation.NOT_SUPPORTED`). 쿼리는 리포지토리가 자기 트랜잭션으로 실행합니다.
- 공연 목록과 순서는 캐시하지 않아서 항상 최신입니다.
- 테스트는 "캐시 유지 시간 안에는 새 공연이 생겨도 건수가 그대로다"를 확인하고, 캐시를 끄면 실패하는 것까지 확인했습니다.

결과: 전체 p95 362ms → 214ms, 처리량 118 → 167회/초, MySQL CPU 4.25코어 → 1.85코어

### 남은 것

- 지금 DB 쿼리 1위는 좌석 조회(평균 1.4ms)이고, 실제 쿼리보다 트랜잭션마다 붙는 `SET autocommit`, `SET SESSION TRANSACTION READ ONLY/WRITE`, `COMMIT` 왕복의 합이 더 큽니다. 다음에 줄일 곳입니다. → 15장에서 줄였습니다.
- 조회만 측정했습니다. 예매·결제처럼 비관적 락을 잡는 쓰기 요청을 섞으면 다른 병목이 보일 수 있습니다. → 14장에서 측정했습니다.
- 데이터를 키우고 나서 화면 버그도 하나 찾았습니다. 좌석 화면이 좌석을 100개까지만 불러와서, 200석이 넘는 공연장에서는 뒤쪽 좌석이 보이지 않습니다. 공연장이 20석뿐이던 데모 데이터에서는 드러나지 않았습니다. → 화면이 전체 건수만큼 페이지를 넘겨 받도록 고쳤습니다.

## 14. 결제가 몰리자 좌석 조회까지 느려진 문제 (쓰기 부하)

13장은 조회만 측정했습니다. 이번에는 비관적 락을 잡는 예매와 PG를 거치는 결제를 섞어서 쟀습니다. 데이터와 환경은 13장과 같고, 시나리오는 [perf/k6/book.js](../perf/k6/book.js)입니다.

- **hot (예매 오픈 순간)**: 한 회차의 좌석 20개를 200명 또는 1,000명이 동시에 한 번씩 예매합니다. 그동안 20명은 같은 회차 좌석 현황을 계속 새로고침합니다.
- **flow (평소 예매)**: 각자 아무 회차에서 빈 좌석 하나를 골라 예매하고 데모 결제를 합니다. 데모 결제는 실제 PG 통신 시간을 흉내 내려고 1.5초를 기다립니다.

### 예매 오픈: 정확성은 그대로

| 동시 예매 | 성공 | 409(이미 예매됨) | 예매 p95 | 좌석 새로고침 p95 |
| --- | --- | --- | --- | --- |
| 200명 → 20석 | 20 | 180 | 162~181ms | 15ms |
| 1,000명 → 20석 | 20 | 980 | 532~570ms | 15~18ms |

여러 번 돌려도 매번 정확히 20건만 성공했습니다. 끝나고 DB 전체를 확인했을 때 한 좌석에 유효한 티켓이 두 장인 경우는 0건, 회차의 잔여석 수(`available_seat_count`)와 실제 빈 좌석 수가 다른 회차도 0건이었습니다. 1,000명일 때 예매 p95가 늘어난 건 같은 좌석 행의 락을 차례로 기다리기 때문이고, 그동안 좌석 새로고침은 p95 15ms 정도로 영향이 거의 없었습니다.

측정 스크립트 버그도 하나 있었습니다. 처음에 401이 20건씩 나와서 보니, k6의 `__VU` 번호는 시나리오를 가리지 않고 매기는 번호라 새로고침용 VU 20명이 1~20번을 먼저 가져갔습니다. 그래서 예매 VU 일부가 로그인 토큰 배열 밖을 읽고 있었습니다. 시나리오 안에서의 반복 번호(`exec.scenario.iterationInTest`)로 회원을 고르게 고쳤습니다.

### 평소 예매: 300명에서 모든 API가 함께 느려짐

| flow, 60초 | 결제 성공 | 결제 p95 | 예매 p95 | 좌석 조회 p95 |
| --- | --- | --- | --- | --- |
| 100명 | 3,830건 | 1.66s | 94ms | 57ms |
| 300명 | 7,692건 | 2.06s | 539ms | 531ms |

300명이 되자 결제만이 아니라 혼자 부르면 10ms 안팎인 예매와 좌석 조회까지 p95가 500ms를 넘었습니다. 13장처럼 커넥션 풀이 모자란 줄 알았는데, 부하를 거는 중에 스레드 덤프(`jstack`)를 떠 보니 달랐습니다.

- Tomcat 요청 스레드 200개 중 **199개가 `DemoPgClient`의 PG 응답 대기** 중이었습니다.
- DB 커넥션을 기다리는 스레드(`HikariPool.getConnection`)는 **0개**였습니다.

결제는 OSIV를 끄고(6장) PG 통신을 트랜잭션 밖으로 빼 두어서(2장) PG를 기다리는 동안 DB 커넥션은 잡지 않습니다. 하지만 요청 스레드는 응답이 올 때까지 계속 붙잡고 있습니다. 결제 1건이 스레드 하나를 1.5초씩 쓰니 스레드 200개로는 초당 133건 정도가 한계이고, 결제가 스레드를 다 차지하면 좌석 조회 같은 가벼운 요청도 빈 스레드가 날 때까지 기다립니다. 데모 결제의 1.5초는 실제 토스 승인 API를 부르는 시간을 흉내 낸 값이라, 운영에서 결제가 몰려도 같은 일이 생깁니다.

### 가상 스레드로 처리

방법은 세 가지를 봤습니다.

- Tomcat 스레드 수를 늘린다: 설정 한 줄이지만 한계를 조금 뒤로 미룰 뿐이고, 스레드마다 메모리를 차지합니다.
- PG 호출을 비동기(WebClient 등)로 바꾼다: 결제 흐름 전체를 다시 짜야 합니다.
- **가상 스레드(Java 21)**: 요청을 가상 스레드에서 처리하면, I/O나 `sleep`으로 기다리는 동안 실제 OS 스레드를 놓아줍니다. 코드는 그대로 두고 동기 방식 그대로 쓸 수 있습니다.

세 번째를 골랐습니다. Java를 17에서 21로 올리고(빌드 toolchain, Dockerfile, CI) `spring.threads.virtual.enabled=true`를 켰습니다. 비교가 공정하도록, Java 21로 올린 상태에서 가상 스레드만 끄고 켜서 같은 조건으로 쟀습니다.

| flow 300명, 60초 (Java 21) | 결제 성공 | 결제 p95 / p99 | 예매 p95 | 좌석 조회 p95 |
| --- | --- | --- | --- | --- |
| 플랫폼 스레드 (Tomcat 200) | 7,597건 | 2.21s / 3.11s | 680ms | 590ms |
| 가상 스레드 | **10,905건** | **1.88s / 2.18s** | **231ms** | **193ms** |

결제 처리량은 44% 늘었고, 예매·좌석 조회 p95는 3분의 1 정도로 줄었습니다. 같은 부하에서 다시 스레드 덤프를 떠 보니(`jcmd Thread.dump_to_file`) 가상 스레드 약 300개 중 280개 정도가 PG를 기다리고 있었지만 OS 스레드를 붙잡지는 않았습니다. 이제 남은 대기는 DB 커넥션(풀 10개)을 기다리는 4~34개였습니다. 병목이 스레드에서 DB 커넥션으로 옮겨 간 것입니다.

예매 오픈(1,000명 → 20석)도 가상 스레드로 다시 돌렸습니다. 결과는 그대로 정확히 20석, 중복 0건이었고 예매 p95(532~599ms)도 비슷했습니다. 이 경우는 스레드가 아니라 같은 행의 DB 락을 기다리는 시간이 대부분이라 가상 스레드로 달라질 게 없습니다. 테스트 152개는 Java 21 + 가상 스레드에서도 모두 통과했습니다.

### 남은 것

- 가상 스레드는 요청을 무제한으로 받아들이기 때문에, 이제는 DB 커넥션 풀(10개)이 사실상 동시 처리량을 정합니다. 커넥션을 기다리다 30초(Hikari 기본값)를 넘기면 실패합니다. 풀 크기와 대기 시간은 운영 서버(t2.micro) 사양에 맞춰 따로 정해야 합니다. → 15장에서 재 보고 10으로 두었습니다.
- Java 21에서는 `synchronized` 블록 안에서 기다리면 가상 스레드가 OS 스레드에 고정(pinning)됩니다. 지금 코드에는 `synchronized`가 없고 MySQL 드라이버(Connector/J 9.x)도 `ReentrantLock`을 쓰지만, 앞으로 라이브러리를 추가할 때는 확인해야 합니다.
- 예매 오픈 때 409를 받을 요청도 좌석 행 락을 기다린 뒤에야 실패합니다. 락을 잡기 전에 좌석 상태를 먼저 보고 바로 거절하면 대기열이 짧아질 수 있습니다.
- k6·앱·MySQL이 한 PC에서 돌아가는 로컬 측정입니다.

## 15. 쿼리보다 트랜잭션 부가 명령이 더 많던 문제

13장 끝에 남겨 둔 것입니다. 13장과 같은 조회 부하(100명, 60초)를 걸고 `performance_schema`로 명령별 실행 횟수를 세 보니, 실제 쿼리보다 트랜잭션을 열고 닫는 명령이 훨씬 많았습니다.

| 명령 (60초) | 실행 횟수 | 누적 시간 |
| --- | --- | --- |
| `SET autocommit = ?` | 210,835 | 13.2s |
| `SET SESSION TRANSACTION READ ONLY` | 105,669 | 6.6s |
| `SET SESSION TRANSACTION READ WRITE` | 105,638 | 6.4s |
| `COMMIT` | 105,742 | 6.3s |
| 실제 쿼리 (상위 8종 합) | 약 12만 | 약 49s |

`@Transactional(readOnly = true)` 하나가 DB에 보내는 명령은 이렇습니다.

```
SET autocommit=0                       -- 트랜잭션 시작 (풀의 커넥션 기본값이 autocommit=true라서)
SET SESSION TRANSACTION READ ONLY      -- readOnly=true를 서버에 알림
SELECT ...                             -- 실제 쿼리
COMMIT
SET SESSION TRANSACTION READ WRITE     -- 커넥션을 풀에 돌려주기 전에 원래대로
SET autocommit=1
```

쿼리 하나에 왕복이 6번이고, 부가 명령이 DB 시간의 약 40%였습니다.

### 1. 같은 값을 다시 보내지 않게 (효과 없음)

처음엔 Connector/J의 `useLocalSessionState=true`를 켰습니다. 드라이버가 세션 상태를 기억해 두었다가 이미 같은 값이면 SET을 보내지 않는 옵션입니다. 횟수가 그대로였습니다. 같은 값을 또 보내는 게 아니라 트랜잭션마다 실제로 켰다가 끄고 있었기 때문입니다.

### 2. 커넥션을 처음부터 autocommit=false로

- Hikari `auto-commit: false`: 풀의 커넥션을 처음부터 autocommit=false로 만듭니다.
- Hibernate `provider_disables_autocommit: true`: "커넥션이 이미 autocommit=false다"라고 알려서, 트랜잭션을 시작할 때 확인하고 바꾸는 일을 하지 않게 합니다.

`SET autocommit` 21만 번이 0이 됐습니다.

autocommit=false면 트랜잭션 밖에서 DB를 쓴 커넥션은 풀에 돌아갈 때 롤백됩니다. 쓰기가 조용히 사라지지 않을까 확인했습니다. JPA는 트랜잭션 밖에서 저장·수정하면 예외를 내고, 리포지토리의 `save()`는 자기 트랜잭션으로 커밋합니다. 실제로 측정 중 `ROLLBACK`이 1분에 91번 보여서 찾아보니, 공연 목록 전체 건수 캐시가 만료돼 DB에서 다시 셀 때(트랜잭션을 일부러 열지 않는 메서드, 13장) 생기는 읽기 롤백이었습니다. 빈 DB에서 띄웠을 때 Flyway 마이그레이션 11개와 관리자 계정 생성(트랜잭션 밖 `ApplicationRunner`)도 정상이었습니다.

### 3. read-only를 서버에 알리지 않게

Connector/J `readOnlyPropagatesToServer=false`(운영 프로필만)로 `READ ONLY`/`READ WRITE` 21만 번도 없앴습니다. 대신 잃는 것이 있습니다.

- `readOnly=true`는 Hibernate 쪽에서는 그대로 동작합니다(flush 생략, 스냅샷을 안 만듦).
- 서버가 읽기 전용 트랜잭션에서 쓰기를 거부해 주는 안전장치는 없어집니다. 읽기 전용 메서드에서 실수로 쓰면 DB가 막아 주지 않습니다.
- InnoDB의 읽기 전용 트랜잭션 최적화도 받지 못하지만, 측정에서는 왕복을 줄인 효과가 훨씬 컸습니다.

### 결과 (조회 100명, 60초)

| | 60초 반복 횟수 | 전체 p95 | 좌석 p95 | 트랜잭션당 명령 |
| --- | --- | --- | --- | --- |
| 바꾸기 전 (2번 측정) | 14,666 ~ 15,131 | 138 ~ 161ms | 105 ~ 114ms | 6 |
| 2. autocommit=false | 19,064 | 113ms | 84ms | 4 |
| 3. + read-only 안 알림 | 27,450 ~ 32,118 | 62 ~ 77ms | 53 ~ 62ms | 2 (쿼리 + COMMIT) |

같은 부하에서 2배 가까이 처리했습니다. k6가 출력하는 "초당 반복"은 준비 단계(가상 사용자 로그인) 시간까지 나눈 값이라 실행마다 흔들려서, 여기서는 60초 동안의 반복 횟수로 비교했습니다. 테스트 152개는 H2와 MySQL 8.0 양쪽에서 통과했습니다.

### 커넥션 풀 크기는 그대로 10

14장에서 가상 스레드로 바꾼 뒤 남은 대기는 커넥션 풀(10개)이었습니다. 왕복을 줄인 상태에서 예매·결제 300명으로 풀 크기만 바꿔 쟀습니다.

| 예매·결제 300명, 60초 | 결제 성공 | 예매 p95 | 좌석 조회 p95 |
| --- | --- | --- | --- |
| 14장 (가상 스레드, 풀 10, 왕복 그대로) | 10,905건 | 231ms | 193ms |
| 왕복 줄인 뒤 풀 10 | 11,308건 | 122ms | 92ms |
| 풀 20 | 11,468건 | 94ms | 59ms |
| 풀 40 | 11,440건 | 78ms | 51ms |

결제 건수는 풀을 늘려도 그대로였습니다. 300명이 한 번에 약 1.6초(좌석 조회 + 예매 + PG 1.5초) 걸리는 흐름을 반복하면 이론상 최대가 초당 약 187건인데, 풀 10에서 이미 초당 188건이었습니다. 서버가 아니라 시나리오가 한계였습니다. 풀을 늘리면 p95가 조금 줄지만, 운영은 t2.micro 한 대에서 MySQL까지 같이 돌아서 커넥션을 늘리면 MySQL 메모리가 늘어납니다. 그래서 10으로 두었습니다. 커넥션이 오래 걸리는 쿼리 하나에 묶이는 문제(13장)를 먼저 줄이는 쪽이 풀을 키우는 것보다 효과가 컸습니다.

## 16. 한 좌석에 몰린 요청이 락 앞에 한 줄로 서던 문제

외부 기술 피드백에서 "좌석 잠금은 합격, 남은 건 성능"이라며, 한 좌석에 100·300개 요청을 동시에 보낸 응답 시간(300개일 때 p90 2.7초)을 받았습니다. p95 100ms처럼 목표를 세우고 병목을 하나씩 줄여 보라는 의견이었습니다. 13~15장을 반영한 서버에서 같은 상황을 k6로 재현했습니다(`book.js`의 `MODE=hot`, `SEATS=1`, 각 3회).

| 한 좌석 동시 예매 | p50 | p95 | p99 |
| --- | --- | --- | --- |
| 100명 | 114~132ms | 175~200ms | 181~208ms |
| 300명 | 310~346ms | 497~571ms | 509~599ms |

목표는 300명 p95 100ms로 잡았습니다.

### 원인: 실패할 요청도 락을 받아야 실패할 수 있었음

응답 시간이 인원에 거의 비례해서(300명이면 한 건에 약 1.7ms씩) 늘었습니다. 요청들이 한 줄로 처리된다는 뜻입니다. 예매는 좌석을 `SELECT ... FOR UPDATE`로 잠근 뒤에 상태를 봅니다. 그래서 이미 팔린 좌석을 노린 299건도 앞 요청이 락을 놓을 때까지 하나씩 기다렸다가, 락을 받고 나서야 "이미 예매됨"을 확인하고 롤백했습니다.

### 1. 팔린 좌석은 락 없이 먼저 거절

예매 맨 앞에서 락 없이 "고른 좌석 중 팔린 좌석 수"만 먼저 세고, 1개 이상이면 바로 409(`SEAT_ALREADY_RESERVED`)로 거절합니다.

- 락 없는 읽기라 여기를 통과해도 뒤의 락 조회에서 다시 확인합니다. 정확성은 그대로 락이 지키고, 이 확인은 확실히 실패할 요청만 걸러냅니다.
- 좌석을 엔티티로 읽지 않고 숫자로만 받습니다. 엔티티로 읽으면 영속성 컨텍스트에 남아서, 뒤의 락 조회가 락을 잡고도 이 시점의 옛 상태를 그대로 돌려받습니다(1장에서 겪은 문제).
- 회귀 테스트(`SoldSeatFastRejectTest`): 팔린 좌석의 락을 다른 트랜잭션이 3초 동안 쥐고 있어도 1초 안에 409로 거절되는지 봅니다. 이 확인을 빼면 락을 기다리다 락 타임아웃 예외로 실패하는 것까지 확인했습니다.

| 300명 → 1석 | p50 | p95 | p99 |
| --- | --- | --- | --- |
| 바꾸기 전 | 310~346ms | 497~571ms | 509~599ms |
| 팔린 좌석 먼저 거절 | 100~120ms | 113~163ms | 135~177ms |
| (비교) DB 조회 1번뿐인 회차 단건 조회 | 99~124ms | 147~174ms | 177~222ms |

100명일 때는 p95 67~78ms로 목표 안에 들어왔습니다. 300명은 113~163ms로 목표에 조금 못 미치지만, DB 조회 한 번뿐인 가장 가벼운 API를 같은 방식(300개 동시)으로 불러도 p95가 147~174ms였습니다. 예매 로직이 아니라 "한 PC에서 Docker 안의 k6가 요청 300개를 한꺼번에 여는 비용"이 바닥입니다. 여기서 더 내리려면 측정 위치부터 분리해야 해서 이 단계에서 멈췄습니다.

### 2. 좌석 여러 개면: 회차 행 하나에 몰림

1,000명이 한 회차의 좌석 20개를 노리는 경우는 1번 이후에도 p95가 555~952ms로 거의 그대로였습니다. 이번에는 `performance_schema`로 DB가 어디서 시간을 쓰는지 직접 봤습니다.

- 1,000건 중 946건은 락 없이 바로 거절됐고, 좌석 락까지 간 건 50건뿐이었습니다. 1번은 제대로 동작하고 있었습니다.
- 대신 회차의 잔여석 수를 줄이는 `UPDATE schedule`이 20번 실행됐는데, 평균 145ms, 최대 397ms가 전부 락 대기였습니다. 서로 다른 좌석을 산 20명이 같은 회차 행 하나를 차례로 잠그고 있었습니다. 이 20개 트랜잭션이 기다리는 동안 커넥션(10개)을 쥐고 있으니, 바로 거절될 요청들도 커넥션을 기다렸습니다.
- 그 UPDATE가 트랜잭션 중간에 있어서, 뒤의 예약·티켓 INSERT가 끝날 때까지 락을 쥐고 있었습니다. 저장(flush)을 먼저 하고 감소를 커밋 직전으로 옮겼더니 평균 대기가 88~120ms로 줄었지만, 근본적으로는 그대로입니다.

### 남은 것

- 회차 행 하나에 그 회차의 모든 예매가 몰리는 구조가 남은 병목이었습니다. 잔여석 수를 좌석 테이블에서 바로 세는 방식으로 바꿔서 해결했습니다(17장).
- 1,000명 → 20석에서도 성공은 매번 정확히 20건이었고, DB 전체에서 중복 티켓 0건, 잔여석 수 불일치 0건이었습니다. 테스트 153개는 H2·MySQL 8.0 양쪽에서 통과했습니다.

## 17. 서로 다른 좌석을 산 예매끼리도 회차 행 앞에 줄을 서던 문제

16장에서 남긴 병목입니다. 회차의 잔여석 수(`schedule.available_seat_count`)는 예매하면 줄이고, 취소나 자동 만료로 좌석이 돌아오면 늘렸습니다. 이 UPDATE가 회차 행을 잠그기 때문에, 같은 회차라면 좌석이 하나도 겹치지 않는 예매끼리도 행 하나를 차례로 기다렸습니다.

### 카운터가 지키던 것

카운터 UPDATE에는 `잔여석 >= 고른 수` 조건이 붙어 있었고, 0건이면 `NOT_ENOUGH_SEATS`로 실패했습니다. 그런데 이 검사보다 먼저 좌석을 하나씩 비관적 락으로 잡고 상태를 확인합니다. 좌석이 이미 팔렸으면 거기서 실패하므로, 카운터 조건이 걸리는 경우는 실제로 없었습니다. 카운터는 정확성에는 관여하지 않고, 회차 목록의 "잔여 n석" 표시에만 쓰이고 있었습니다.

### 바꾼 것: 잔여석을 좌석 상태에서 셈

- 예매·취소·자동 만료에서 카운터 UPDATE를 지웠습니다. 쓰지 않게 된 `NOT_ENOUGH_SEATS`도 지웠습니다.
- 회차 목록과 회차 단건은 `select schedule_id, count(*) from seat where schedule_id in (...) and status = 'AVAILABLE' group by schedule_id`로 잔여석을 셉니다. 회차가 여러 개여도 쿼리 한 번이고, 다 팔린 회차는 결과에 없어서 0으로 채웁니다.
- V12에서 `(schedule_id, status)` 인덱스를 추가하고 `available_seat_count` 컬럼을 지웠습니다. 컬럼을 남겨 두면 아무도 고치지 않는 옛 값이 엔티티에 남아 잘못 읽힐 수 있어서입니다. 좌석 350만 건 기준 마이그레이션은 13초였습니다. MySQL은 새 인덱스가 외래 키 컬럼으로 시작해서, 외래 키용으로 자동으로 만들었던 인덱스를 새 인덱스로 대신했습니다.
- 처음에는 컨트롤러가 회차 조회와 잔여석 count를 따로 불러서 요청 하나가 커넥션을 두 번 빌렸습니다. 서비스에서 한 트랜잭션으로 합쳤습니다.

count 쿼리는 인덱스만 읽고 끝납니다(회차 4개, 좌석 963행 기준 0.33ms).

```
-> Covering index range scan on s using idx_seat_schedule_status
   over (schedule_id = 14 AND status = 'AVAILABLE') OR ...  (actual time=0.0357..0.199 rows=963)
```

### 결과

회차 단위 경합만 보려고 `book.js` hot에 `SPREAD=1`을 추가했습니다. 사람마다 다른 좌석을 고르게 해서, 좌석은 하나도 겹치지 않고 회차만 같습니다. 200명이 동시에 예매하면 200건이 모두 성공합니다. 각 3회, 매번 다른 회차로 쟀습니다.

| 200명 → 같은 회차의 다른 좌석 200개 | p50 | p95 | 평균 |
| --- | --- | --- | --- |
| 회차 잔여석 카운터 | 477~659ms | 830ms~1.11s | 470~689ms |
| 좌석 상태에서 세기 | 145~179ms | 243~316ms | 145~196ms |

바꾸기 전에는 `UPDATE schedule`이 한 번 돌릴 때마다 200번 실행됐고, 평균 30~33ms, 락 대기 합계는 6.0~6.5초였습니다. 바꾼 뒤에는 이 문장이 DB 기록에서 없어졌습니다.

16장의 1,000명 → 20석은 p95 445~660ms(바꾸기 전 3회)에서 269~672ms(바꾼 뒤 6회)로, 측정 흔들림 안이었습니다. 회차 행까지 가는 건 성공하는 20건뿐이고, 나머지 980건은 16장의 선확인에서 바로 거절됩니다. 그래서 응답 시간은 1,000개 연결이 한꺼번에 열리는 비용이 정합니다. 바꾸기 전 이 20건의 UPDATE 락 대기는 평균 17~93ms였습니다.

조회 쪽(13장의 100명 반복)은 회차 목록 p95가 82·106ms(바꾸기 전)에서 117·84ms(바꾼 뒤)였습니다. 같은 서버로 다시 돌려도 처리량이 1.7만~2.4만 회로 흔들려서, count 쿼리 하나가 늘어난 차이는 보이지 않았습니다.

정합성: 모든 측정에서 좌석 하나에 활성 티켓이 2장 이상인 경우는 0건이었습니다. 잔여석을 확인하던 테스트들은 회차 목록 API와 같은 count 쿼리로 확인하게 바꿨고, 테스트 153개가 H2와 MySQL 8.0(빈 DB에서 Flyway V1~V12) 양쪽에서 통과했습니다.

### 남은 것

- 측정할 때마다 회차를 바꿔야 해서, 바꾸기 전 서버는 로컬 성능 DB를 V11 상태로 되돌린 뒤 다시 띄워 쟀습니다(컬럼을 다시 만들고 좌석 상태로 값을 채움). 두 측정 사이에 다른 조건은 바꾸지 않았지만, 같은 시각에 번갈아 잰 것은 아닙니다.
- 1,000명 → 20석처럼 연결이 한꺼번에 몰리는 경우는 측정 환경(한 PC의 Docker 안 k6)이 먼저 한계에 닿습니다. 더 보려면 부하 발생기를 다른 장비로 분리해야 합니다.

### 나중에 발견: 좌석 목록 순서가 바뀜

배포 뒤 운영 화면에서 예약된 좌석이 섞인 회차의 좌석이 1, 4, 6, 7, …(빈 좌석) 다음에 2, 3, 5, …(예약된 좌석) 순서로 나왔습니다. 좌석 목록 쿼리에 순서가 없어서 MySQL이 고른 인덱스 순서를 그대로 따랐는데, 빈 DB에서 V12를 적용하면 MySQL이 외래 키용 인덱스 대신 새 `(schedule_id, status)` 인덱스를 쓰면서 상태 순서로 읽었기 때문입니다. 로컬 성능 DB는 되돌리는 과정에서 외래 키 인덱스가 다시 생겨 있어서 보이지 않았습니다.

화면만의 문제가 아니었습니다. 좌석 화면은 100개씩 페이지를 나눠 받는데, 순서가 정해져 있지 않으면 받는 사이 좌석 상태가 바뀔 때 같은 좌석이 두 번 오거나 빠질 수 있습니다. 좌석 번호(+id) 순서를 명시했고(`findByScheduleIdOrderBySeatNumberAscIdAsc`), Flyway로 만든 MySQL에서 수정 전 `[1, 4, 6, 7, 9, 10]`이 나오던 것을 `SeatListOrderTest`로 남겼습니다.

또 하나 알게 된 것: 그동안 "MySQL에서도 통과"라고 한 테스트는 로컬 프로필 그대로 돌려서 테이블을 Hibernate가 만들었고, V12 인덱스가 없었습니다. 지금은 `SPRING_FLYWAY_ENABLED=true`, `SPRING_JPA_HIBERNATE_DDL_AUTO=validate`로 Flyway 스키마에서 돌립니다.

## 18. 금액 규칙: 좌석 등급과 취소 수수료

외부 기술 피드백에서 "금액 정책이 단순하다"는 의견을 받았습니다. 당시에는 회차를 만들면 모든 좌석이 VIP 150,000원으로 생겼고, 취소는 공연 전이기만 하면 항상 전액 환불이었습니다. 실제 예매처처럼 좌석 등급별 가격을 두고, 공연까지 남은 날짜에 따라 취소 수수료를 떼게 했습니다.

### 1. 좌석 등급

- 회차 등록 요청에 `grades`(무대에서 가까운 순서의 등급별 좌석 수·가격)를 받습니다. 목록 순서대로 1번 좌석부터 등급을 붙입니다. 예를 들어 VIP 10석, R 30석이면 1~10번이 VIP, 11~40번이 R입니다.
- 비우면 기본 배치(VIP 20%·R 30%·S 30%·나머지 A, 150,000/120,000/90,000/60,000원)를 씁니다. 기존 API 사용처와 로컬 테스트 데이터는 그대로 동작합니다.
- 등급별 좌석 수 합이 좌석 수와 다르거나 같은 등급이 두 번 나오면 `INVALID_SCHEDULE`(400)로 막습니다. 0석이나 없는 등급 이름은 요청 검증에서 400입니다.
- 등급은 문자열에서 enum(`SeatGrade`)으로 바꿨습니다. DB 값은 기존과 같은 `'VIP'` 문자열이라 운영 데이터를 바꿀 필요가 없었습니다.
- 관리자 화면은 좌석 수를 넣으면 기본 배치로 표를 채우고, 등급마다 좌석 번호 범위를 보여줍니다. 합계가 좌석 수와 다르면 등록 버튼을 눌러도 서버에 보내지 않습니다.

### 2. 취소 수수료

| 취소 시점 | 수수료 |
| --- | --- |
| 예매 후 24시간 안 (공연 3일 전까지 한 예매만) | 무료 |
| 공연 7일 전까지 | 무료 |
| 공연 6~3일 전 | 10% |
| 공연 2일 전 ~ 시작 전 | 30% |
| 공연 시작 후 | 취소 불가 (기존 규칙) |

- 며칠 전인지는 시각이 아니라 날짜로 셉니다. 공연이 11월 20일 19시면 11월 13일 23시 59분까지 무료이고, 14일 0시부터 10%입니다. 시각으로 세면 같은 날 오전과 저녁에 구간이 달라져서 안내하기 어렵습니다.
- 예매 후 24시간 무료 규칙은 공연 2일 전부터 한 예매에는 적용하지 않습니다. 적용하면 공연 직전에 사서 무료로 무를 수 있습니다.
- 경계값(7일 전 날 23:59 / 6일 전 0:00, 3일 전 / 2일 전, 24시간 직전·직후)은 `CancelFeePolicyTest`로 확인합니다.

### 3. 계산은 한 번, PG와 DB에 같은 금액

취소는 원래 "환불 대상 확인(짧은 트랜잭션) → PG 환불(트랜잭션 밖) → DB 반영(짧은 트랜잭션)" 순서입니다(2·5장). 각 단계에서 수수료를 따로 계산하면, 그 사이 자정을 넘길 때 PG에 보낸 금액과 DB에 적은 금액이 달라질 수 있습니다. 그래서 첫 단계에서 환불 계획(`RefundPlan`: paymentKey, 결제한 PG, 수수료·환불액)을 한 번 만들고, PG 요청과 DB 기록이 모두 이 값을 씁니다. 결제 기록에는 `cancel_fee`, `refunded_amount`를 남깁니다(V13). 그 전에 취소된 결제는 모두 전액 환불이었으므로 마이그레이션에서 수수료 0, 환불액 = 결제 금액으로 채웠습니다.

화면은 취소 버튼을 누르면 `GET /api/v1/reservations/{id}/refund-quote`로 같은 계산 결과를 받아 결제 금액·수수료·환불 금액을 보여주고, "취소 확정"을 눌러야 취소합니다. 미리 본 뒤 날짜가 바뀌어 구간이 달라졌다면, 실제 취소 요청 시점의 금액이 적용됩니다.

### 4. 부분 환불이라 새로 생긴 위험: 환불이 두 번 나가는 경우

전액 취소만 있을 때는 이런 경우가 안전했습니다. PG 환불은 성공했는데 DB 반영 전에 서버가 실패하고, 고객이 다시 취소를 누르는 경우입니다. 토스가 두 번째 요청을 "이미 취소된 결제"로 거절했기 때문입니다. 부분 환불은 남은 금액이 있는 한 다시 취소할 수 있어서, 같은 상황이면 수수료를 뗀 환불이 한 번 더 나갈 수 있습니다.

- 토스 취소 요청에 `Idempotency-Key: cancel-{paymentKey}`를 붙였습니다. 이 서비스에서는 결제 하나를 한 번만 취소하므로, 같은 결제의 취소는 몇 번 보내도 토스가 처음 결과만 돌려줍니다.
- 이미 취소된 예약은 PG를 부르기 전에 409(`RESERVATION_ALREADY_CANCELLED`)로 막습니다. 원래는 PG 환불 요청이 먼저 나가고 DB 단계에서야 거절됐습니다.
- 돌려줄 금액이 0원(0원 좌석)이면 PG를 부르지 않습니다.
- 결제 반영 실패 시의 보상 취소(3장)는 지금처럼 전액 취소입니다(`cancelAmount` 없음).

### 확인한 것

- 로컬에서 구간별 예약을 만들어 미리 보기와 취소를 했습니다. 11월 15일 공연은 무료, 4일 뒤 공연 240,000원은 수수료 24,000원·환불 216,000원, 2일 뒤 공연 150,000원은 수수료 45,000원·환불 105,000원이었고, 결제 기록에도 같은 값이 남았습니다. 이미 취소된 예약에 미리 보기를 요청하면 409였습니다.
- 테스트 168개가 H2와 MySQL 8.0(빈 DB에서 Flyway V1~V13) 양쪽에서 통과했습니다. 추가한 테스트는 수수료 구간 경계, HTTP 미리 보기 → 취소 → 결제 기록, 토스 요청 본문(`cancelAmount`)·멱등 키, 0원 결제의 PG 생략, 등급 배치·검증입니다.

### 남은 것

- 수수료 규칙이 코드에 하나뿐이라 공연마다 다르게 둘 수 없습니다. 공연(또는 회차)에 정책을 붙이려면 구간을 데이터로 저장해야 합니다.
- 토스 부분 환불은 테스트 서버로 요청 형식만 확인했습니다. 실제 토스 테스트 결제로 부분 취소까지는 해 보지 않았습니다.
- 좌석 등급은 번호 순서로만 나뉩니다. 층·구역 같은 모양은 좌석에 행·열 정보가 있어야 그릴 수 있습니다.

## 19. 예매 오픈 순간 1,000명이 몰릴 때: 오픈 시각과 대기열

외부 기술 피드백의 "다른 핵심 기능" 의견으로 예매 오픈과 대기열을 만들었습니다. 그 전에는 회차를 등록하는 순간부터 예매가 열려 있어서, 정해진 시각에 사람이 한꺼번에 몰리는 상황 자체가 없었습니다.

### 1. 예매 오픈 시각

- 회차에 `booking_open_at`(V14)을 두고 관리자가 회차를 등록할 때 정합니다. 비우면 지금처럼 바로 예매할 수 있고, 공연 시작 이후로 잡으면 `INVALID_SCHEDULE`(400)입니다.
- 오픈 전 예매 요청은 좌석 락을 잡기 전에 `BOOKING_NOT_OPEN`(409)으로 거절합니다. 고른 좌석들의 회차를 락 없이 먼저 읽어 확인합니다(16장의 선확인과 같은 자리).
- 화면은 오픈 전이면 좌석 대신 카운트다운을 보여주고, 시각이 되면 다시 물어서 넘어갑니다.

### 2. 대기열 (Redis)

오픈 직후 1,000명이 좌석 화면과 예매 API를 동시에 부르면, 대부분은 이미 팔린 좌석에 부딪혀 다시 시도하면서 부하만 더합니다. 줄을 세워 일정 인원씩만 좌석 화면에 들여보내게 했습니다.

- 오픈 시각부터 30분 동안만 운영합니다. 그 밖의 시간과 오픈 시각이 없는 회차는 Redis를 부르지 않습니다.
- 줄 서기: Sorted Set `queue:{회차}:waiting`에 줄 선 시각을 점수로 넣습니다. 다시 서도 순번이 유지됩니다(`ZADD NX`).
- 입장: 1초마다 앞에서 20명을 꺼내(`ZPOPMIN`) `queue:{회차}:admitted:{회원}` 키를 10분 TTL로 줍니다. `ZPOPMIN`이라 서버가 여러 대여도 같은 사람을 두 번 꺼내지 않습니다.
- 예매 API는 좌석 락 전에 입장 키가 있는지만 보고, 없으면 `QUEUE_ENTRY_REQUIRED`(403)입니다.
- 대기열 운영 중 Redis가 응답하지 않으면 503(`QUEUE_UNAVAILABLE`)입니다. 대기열을 건너뛰고 예매를 열어 주면, 줄 선 사람보다 새로고침한 사람이 먼저 사게 됩니다.
- 서버 메모리에 두면 재시작할 때 줄이 사라지고 서버가 여러 대면 순번이 갈립니다. DB에 두면 2초마다 순번을 묻는 1,000명이 그대로 DB로 갑니다. 그래서 Redis를 붙였습니다(운영은 같은 compose에 64MB, 디스크 저장 없이).
- 1초 스케줄러가 한가할 때 Redis를 부르지 않도록, 지금 줄이 있는 회차 id만 메모리에 들고 돕니다.
- 화면: 대기 화면(내 앞 인원, 예상 대기 시간, 2초마다 다시 물음) → 차례가 되면 좌석 화면과 "N분 안에 예매" 안내.

### 결과 (1,000명 → 367석, 로컬)

`perf/k6/open.js`: 1,000명이 같은 회차에 동시에 들어와 좌석 화면을 열고 빈 좌석 하나를 예매합니다(겹치면 한 번 더).

| 1,000명 → 367석 | 좌석 조회 p95 | 예매 p95 | 결과까지 p50 / 최대 |
| --- | --- | --- | --- |
| 대기열 없음 (2회) | 564~775ms | 542~655ms | 5.2~7.2s / 5.7~30s |
| 대기열 20명/초 (3회) | 11~47ms | 32~272ms | 25.6~27.1s / 52~53s |

API 응답은 10분의 1 아래로 줄었지만, 결과를 받기까지는 훨씬 오래 걸립니다. 대기열은 서버를 지키고 순서를 정하는 장치이지 빨리 끝내 주는 장치가 아닙니다. 입장 속도로 계산하면 367석은 20초 안팎에 다 팔리는데, 나머지 630여 명은 줄 끝까지 기다린 뒤에야 매진을 알았습니다(4절). 중복 판매는 모든 측정에서 0건이었습니다.

### 3. 1,000명 중 16명이 입장하지 못함

첫 측정에서 999명 중 983명만 입장했습니다. 1명은 k6 쪽 연결 실패였고, 15명은 순번을 물었더니 `NOT_IN_QUEUE`(줄에도 없고 입장도 안 함)를 받았습니다. 화면이었다면 다시 줄을 세워 맨 뒤로 보냈을 사람들입니다.

- 입장 처리가 `ZPOPMIN`과 입장 키 `SET`을 따로 보냈습니다. 그 사이에 순번을 물으면 줄에서는 빠졌고 입장 키는 아직 없습니다.
- 순번 조회도 "입장 키 → 줄" 순서로 두 번 물었습니다. 두 조회 사이에 입장 처리가 끼면 둘 다 못 찾습니다.

꺼내기와 입장 키 쓰기를 Lua 스크립트 하나로 묶었습니다. Redis는 스크립트를 중간에 다른 명령 없이 한 번에 실행합니다. 조회는 "줄 → 입장 키" 순서로 바꿨습니다. 입장 처리가 한 번에 끝나므로, 줄에서 못 찾았다면 그 전에 입장 키가 이미 생긴 것입니다. 줄 서기도 "입장했는지 확인 + `ZADD NX`"를 한 스크립트로 묶어, 입장한 사람이 다시 줄에 서지 않게 했습니다.

300명이 줄 선 상태에서 입장 처리를 돌리는 동안 8개 스레드가 모두의 순번을 계속 묻는 테스트를 만들었습니다. 수정 전에는 31건(입장 50명씩), 조회 순서만 남았을 때는 4번 중 3번에서 1~2건이 나왔고, 수정 후에는 6번 반복해 모두 0건이었습니다. 같은 부하를 다시 돌리면 수정 전 1,000명 중 2명이 `NOT_IN_QUEUE`, 수정 후 1,000명 모두 입장했습니다.

### 4. 매진 뒤에도 끝까지 기다리던 문제

위 측정에서 매진 뒤 남은 사람들은 평균 27초, 길게는 52초를 기다려 매진을 확인했습니다. 대기 응답에 남은 좌석 수(`availableSeats`)를 붙이고, 0이면 화면이 "현재 매진" 안내를 띄웁니다. 줄에서 빼지는 않습니다. 결제하지 않은 예약은 10분 뒤 풀리기 때문입니다. 실제로 측정에 쓴 회차는 결제하지 않은 367건이 10분 뒤 회수되어, 매진이던 회차에 다시 367석이 생겼습니다. 1,000명이 2초마다 묻기 때문에 잔여석은 회차당 1초에 한 번만 셉니다.

### 확인한 것

- 테스트: 줄 선 순서대로 입장·입장한 회원만 예매, 운영 시간이 지나면 Redis 없이 예매, 오픈 전 안내, 입장 처리 중 순번 조회, 잔여석·매진 유지(Testcontainers로 띄운 실제 Redis), 오픈 전 거절. 177개가 H2와 MySQL 8.0(Flyway V1~V14) 양쪽에서 통과했습니다.
- 운영 배포: compose에 Redis를 추가하고(포트 비공개, 64MB, 메모리가 차면 지우지 않고 쓰기 거절), 배포 스크립트가 Redis도 함께 올립니다.

### 남은 것

- 운영에서 오픈 시각이 있는 회차로 대기열을 실제로 돌려 보지는 않았습니다. 지금 운영 회차는 모두 오픈 시각이 없어서 Redis를 거치지 않습니다.
- 입장 속도는 초당 20명으로 고정입니다. 서버가 여러 대면 서버마다 스케줄러가 20명씩 꺼내 입장 속도가 서버 수만큼 늘어납니다. 한 서버만 입장을 돌리게 하는 장치가 필요합니다.
- 예상 대기 시간은 "순번 ÷ 20"이라, 앞사람이 떠나거나 입장 시간이 지나는 경우를 반영하지 않습니다. 입장한 뒤 10분 안에 예매하지 않으면 다시 줄 뒤로 갑니다.
- 계정 여러 개로 여러 번 줄 서는 것은 막지 않습니다.
- 로컬에서 1,000명이 동시에 연결을 열면 수백 건이 연결 단계에서 거절(connection refused)됐습니다. Tomcat의 연결 대기열(`accept-count`, 기본 100)을 넘은 것으로 보지만 확인하지 않았고, 측정에서는 줄 서기를 다시 시도하게 했습니다.
